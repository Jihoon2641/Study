# @Transactional 예제 — 커넥션을 눈으로 확인하기

관련 문서: [이론](./트랜잭셔널-이론.md)

---

## 1. 예제 개요

"트랜잭션 = 커넥션"이라는 관계를 **DB 쪽에서 직접 관측**하는 실습 프로젝트를 만든다.

관측 도구 `TxProbe`는 현재 위치에서 다음을 한 번에 기록한다.

| 관측값 | 얻는 방법 | 증명하는 것 |
|---|---|---|
| `backendPid` | `select pg_backend_pid()` | 같은 PID면 같은 물리 커넥션 |
| `activeConnections` | `HikariPoolMXBean#getActiveConnections` | 이 스레드가 풀에서 몇 개를 빌려 쥐고 있는가 |
| `actualTransactionActive` | `TransactionSynchronizationManager` | Spring이 물리 트랜잭션을 열었는가 |
| `dbReadOnly` / `dbIsolation` | `current_setting('transaction_read_only' / 'transaction_isolation')` | `readOnly`/`isolation` 옵션이 실제 DB 세션에 적용됐는가 |

검증하는 개념:

1. 전파 옵션별 커넥션 공유·추가 대여 (`REQUIRED`, `REQUIRES_NEW`, `NOT_SUPPORTED`, `SUPPORTS`, `MANDATORY`, `NESTED`)
2. `readOnly`·`isolation`이 새 트랜잭션에만 적용되고 참여 시 무시됨
3. 롤백 함정: `UnexpectedRollbackException`, checked 예외 커밋, 자기 호출
4. PostgreSQL aborted transaction(`25P02`)과 세이브포인트 복구
5. 트랜잭션 안 외부 호출의 커넥션 점유
6. `REQUIRES_NEW`로 인한 커넥션 풀 데드락과 경계 분리 해법

> 이 문서의 코드는 JDBC(`JdbcTemplate`) 기준이다. 커넥션 동작이 가장 투명하게 드러나기 때문이다. JPA로 바꿨을 때의 차이는 8장 변형 실습 3에서 다룬다.

## 3. 잘못된 코드 먼저

### 3.1 안쪽 실패를 `catch`로 삼키기

```java
@Transactional
public void swallowRequiredFailure(String message) {
    auditRepository.insert("outer-" + message);
    try {
        inner.insertThenFail("inner-" + message);   // @Transactional(REQUIRED), IllegalStateException 발생
    } catch (IllegalStateException e) {
        log.warn("안쪽 실패를 무시하고 계속 진행: {}", e.getMessage());
    }
}
```

**문제**: 예외는 안쪽 프록시의 `TransactionInterceptor`를 먼저 통과한다. 안쪽 경계는 참여 트랜잭션이므로 공유 `ConnectionHolder`에 rollback-only를 찍는다. 바깥이 예외를 삼켜도 커밋 시점에 `UnexpectedRollbackException`이 발생하고 `outer-*`도 롤백된다.

### 3.2 checked 예외

```java
@Transactional
public void insertThenThrowChecked(String message) throws BusinessException {
    auditRepository.insert(message);
    throw new BusinessException("재고 부족");
}
```

**문제**: 기본 롤백 규칙은 `RuntimeException`/`Error`뿐이다. 예외는 호출자에게 전달되지만 **INSERT는 커밋된다.**

### 3.3 자기 호출

```java
public boolean callInternally() {
    return internalTx();                  // this.internalTx() — 프록시를 거치지 않는다
}

@Transactional
public boolean internalTx() {
    return TransactionSynchronizationManager.isActualTransactionActive();
}
```

**문제**: `callInternally()`에서 부른 `internalTx()`는 트랜잭션 없이 실행된다.

### 3.4 PostgreSQL에서 DB 예외를 잡고 계속 진행

```java
@Transactional
public void swallowDuplicateKey(String message) {
    auditRepository.insert(message);
    try {
        auditRepository.insert(message);                  // unique 위반 23505
    } catch (DuplicateKeyException e) {
        log.warn("중복이라 건너뜀");                        // Oracle이면 여기서 계속 진행 가능
    }
    auditRepository.insert(message + "-after");           // PostgreSQL: 25P02 current transaction is aborted
}
```

**문제**: PostgreSQL은 실패한 SQL 이후 트랜잭션 전체를 aborted 상태로 만든다. Oracle에서 이관한 코드가 여기서 깨진다.

### 3.5 트랜잭션 안에서 외부 API 호출

```java
@Transactional
public String placeOrder(long orderId, long amount) {
    auditRepository.insert("order-" + orderId + "-created");
    String paymentId = paymentClient.approve(orderId, amount);   // 수백 ms ~ 수 초
    auditRepository.insert("order-" + orderId + "-paid-" + paymentId);
    return paymentId;
}
```

**문제**: `doBegin`에서 빌린 커넥션을 외부 호출 내내 쥐고 있다. 결제사가 느려지면 커넥션 풀이 고갈되어 결제와 무관한 API까지 멈춘다.

### 3.6 실패 로그를 `REQUIRES_NEW`로 남기기

```java
@Transactional
public void runAndLogFailure(CyclicBarrier barrier, String message) {
    try {
        auditRepository.insert("main-" + message);
        Barriers.await(barrier);
        throw new MainWorkException("main failed: " + message);
    } catch (MainWorkException e) {
        inner.insertInNewTransaction("failed-" + message);   // REQUIRES_NEW: 커넥션 하나 더 요청
        throw e;
    }
}
```

**문제**: 바깥 커넥션을 반납하지 않은 채 두 번째 커넥션을 요청한다. 동시 요청 수 ≥ 풀 크기가 되면 모든 스레드가 서로를 기다리고, 먼저 기다리기 시작한 스레드는 `connection-timeout` 후 반드시 실패한다. 풀 크기 2, 스레드 2개로 재현한다(7장 `PoolDeadlockTest`).

## 4. 개선된 코드

### 4.1 1단계 — 실패를 허용할 구간은 세이브포인트(`NESTED`)로 감싼다

```java
// OuterService
@Transactional
public void swallowNestedFailure(String message) {
    auditRepository.insert("outer-" + message);
    try {
        inner.insertNestedThenFail("nested-" + message);   // @Transactional(NESTED)
    } catch (IllegalStateException e) {
        log.warn("세이브포인트까지만 롤백하고 계속 진행: {}", e.getMessage());
    }
}

@Transactional
public void swallowDuplicateKeyWithSavepoint(String message) {
    auditRepository.insert(message);
    try {
        inner.insertNested(message);                      // 실패하면 ROLLBACK TO SAVEPOINT
    } catch (DuplicateKeyException e) {
        log.warn("중복이라 건너뜀 (세이브포인트 복구)");
    }
    auditRepository.insert(message + "-after");          // aborted 상태가 풀려 정상 실행
}
```

**좋아진 점**
- 커넥션을 추가로 빌리지 않는다(같은 커넥션에 `SAVEPOINT`).
- 안쪽 실패가 rollback-only를 찍지 않는다 — `processRollback`이 `status.hasSavepoint()` 분기로 빠진다.
- PostgreSQL aborted 상태가 `ROLLBACK TO SAVEPOINT`로 해제된다.

**한계**: JPA(`JpaTransactionManager` + Hibernate)에서는 쓸 수 없다. 중복 무시가 목적이면 SQL 자체를 바꾸는 것이 가장 싸다.

```sql
-- PostgreSQL
insert into audit_log(message) values (?) on conflict (message) do nothing;

-- Oracle: ON CONFLICT 문법이 없다
merge into audit_log t
using (select ? as message from dual) s
on (t.message = s.message)
when not matched then insert (message) values (s.message);
```

### 4.2 2단계 — 롤백 규칙을 명시한다

```java
@Transactional(rollbackFor = BusinessException.class)
public void insertThenThrowCheckedWithRollbackFor(String message) throws BusinessException {
    auditRepository.insert(message);
    throw new BusinessException("재고 부족");
}
```

**좋아진 점**: `RuleBasedTransactionAttribute`가 `BusinessException`에 대해 롤백 규칙을 찾는다. 팀 전체 규칙으로 가려면 도메인 예외를 `RuntimeException` 하위로 설계하는 편이 누락 위험이 적다.

### 4.3 3단계 — 자기 호출은 `TransactionTemplate`으로 경계를 코드에 드러낸다

```java
// Java 8+
public boolean callWithTemplate() {
    Boolean active = transactionTemplate.execute(
            status -> TransactionSynchronizationManager.isActualTransactionActive());
    return Boolean.TRUE.equals(active);
}
```

```java
// Java 7 (Spring 3.x/4.x): 람다 대신 익명 클래스
public boolean callWithTemplate() {
    Boolean active = transactionTemplate.execute(new TransactionCallback<Boolean>() {
        @Override
        public Boolean doInTransaction(TransactionStatus status) {
            return TransactionSynchronizationManager.isActualTransactionActive();
        }
    });
    return Boolean.TRUE.equals(active);
}
```

**좋아진 점**: 프록시에 의존하지 않으므로 자기 호출·private 여부와 무관하다. 메서드 일부만 트랜잭션으로 묶을 수 있다. 여러 곳에서 재사용되는 경계라면 별도 빈으로 분리하는 것이 1순위다.

### 4.4 4단계 — 외부 호출을 트랜잭션 밖으로 뺀다

```java
// OrderTxWorker: 짧은 트랜잭션만 담당
@Transactional
public void createPending(long orderId) { auditRepository.insert("order-" + orderId + "-created"); }

@Transactional
public void markPaid(long orderId, String paymentId) { auditRepository.insert("order-" + orderId + "-paid-" + paymentId); }

// OrderService: 트랜잭션 없음. 두 트랜잭션과 외부 호출을 조율한다
public String placeOrder(long orderId, long amount) {
    worker.createPending(orderId);                          // 트랜잭션 1 → 커밋 → 커넥션 반납
    String paymentId;
    try {
        paymentId = paymentClient.approve(orderId, amount); // 커넥션 0개
    } catch (RuntimeException e) {
        worker.markPaymentFailed(orderId);                  // 보상/상태 전이
        throw e;
    }
    worker.markPaid(orderId, paymentId);                    // 트랜잭션 2
    return paymentId;
}
```

**좋아진 점**: 외부 호출 중 active 커넥션이 1 → 0. 대신 "주문은 생성됐는데 결제 결과 반영 전"인 중간 상태가 DB에 보이므로 **상태 컬럼(PENDING/PAID/FAILED)으로 모델링**해야 한다. 원자성을 트랜잭션 대신 도메인 상태로 옮긴 것이다.

### 4.5 5단계 — 실패 로그는 메인 트랜잭션이 끝난 뒤 남긴다

```java
// MainTxWorker
@Transactional
public void run(CyclicBarrier barrier, String message) {
    auditRepository.insert("main-" + message);
    Barriers.await(barrier);
    throw new MainWorkException("main failed: " + message);
}

// FailureLogFacade: 트랜잭션 없음
public void runAndLogFailure(CyclicBarrier barrier, String message) {
    try {
        mainTxWorker.run(barrier, message);
    } catch (MainWorkException e) {
        inner.insertInNewTransaction("failed-" + message);  // 이 시점엔 메인 커넥션이 이미 반납됨
        throw e;
    }
}
```

**좋아진 점**: 한 스레드가 동시에 쥐는 커넥션이 2 → 1. HikariCP 공식 `Tn × (Cm − 1) + 1`에서 `Cm = 1`이 되어 풀 크기 1로도 데드락이 불가능하다.

### 5.4 `config/TxConfig.java`

```java
package com.study.tx.config;

import javax.sql.DataSource;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.jdbc.support.JdbcTransactionManager;

@Configuration
public class TxConfig {

    /**
     * Boot가 자동으로 JdbcTransactionManager를 만들어 주지만, enforceReadOnly를 켜기 위해 직접 정의한다.
     * TransactionManager 빈이 있으면 DataSourceTransactionManagerAutoConfiguration은 물러난다.
     *
     * enforceReadOnly=true: readOnly 트랜잭션 시작 시 "SET TRANSACTION READ ONLY"를 SQL로 실행한다.
     * 드라이버의 Connection#setReadOnly 구현(PgJDBC readOnlyMode 등)에 의존하지 않고 DB가 쓰기를 거부하게 만든다.
     */
    @Bean
    public JdbcTransactionManager transactionManager(DataSource dataSource) {
        JdbcTransactionManager transactionManager = new JdbcTransactionManager(dataSource);
        transactionManager.setEnforceReadOnly(true);
        return transactionManager;
    }
}
```

### 5.5 `probe/TxSnapshot.java` (Java 16+ record)

```java
package com.study.tx.probe;

public record TxSnapshot(
        String label,
        int backendPid,
        boolean actualTransactionActive,
        String transactionName,
        boolean dbReadOnly,
        String dbIsolation,
        int activeConnections) {
}
```

**Java 8 대응 코드** — record가 자동 생성하는 것(생성자, 접근자, `equals`/`hashCode`/`toString`)을 직접 작성한다. 접근자 이름이 `backendPid()`에서 `getBackendPid()`로 바뀌므로 테스트 코드의 호출도 함께 바꿔야 한다.

```java
package com.study.tx.probe;

import java.util.Objects;

public final class TxSnapshot {

    private final String label;
    private final int backendPid;
    private final boolean actualTransactionActive;
    private final String transactionName;
    private final boolean dbReadOnly;
    private final String dbIsolation;
    private final int activeConnections;

    public TxSnapshot(String label, int backendPid, boolean actualTransactionActive, String transactionName,
                      boolean dbReadOnly, String dbIsolation, int activeConnections) {
        this.label = label;
        this.backendPid = backendPid;
        this.actualTransactionActive = actualTransactionActive;
        this.transactionName = transactionName;
        this.dbReadOnly = dbReadOnly;
        this.dbIsolation = dbIsolation;
        this.activeConnections = activeConnections;
    }

    public String getLabel() { return label; }
    public int getBackendPid() { return backendPid; }
    public boolean isActualTransactionActive() { return actualTransactionActive; }
    public String getTransactionName() { return transactionName; }
    public boolean isDbReadOnly() { return dbReadOnly; }
    public String getDbIsolation() { return dbIsolation; }
    public int getActiveConnections() { return activeConnections; }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof TxSnapshot)) return false;
        TxSnapshot that = (TxSnapshot) o;
        return backendPid == that.backendPid
                && actualTransactionActive == that.actualTransactionActive
                && dbReadOnly == that.dbReadOnly
                && activeConnections == that.activeConnections
                && Objects.equals(label, that.label)
                && Objects.equals(transactionName, that.transactionName)
                && Objects.equals(dbIsolation, that.dbIsolation);
    }

    @Override
    public int hashCode() {
        return Objects.hash(label, backendPid, actualTransactionActive, transactionName,
                dbReadOnly, dbIsolation, activeConnections);
    }

    @Override
    public String toString() {
        return "TxSnapshot[label=" + label + ", backendPid=" + backendPid
                + ", actualTransactionActive=" + actualTransactionActive
                + ", transactionName=" + transactionName + ", dbReadOnly=" + dbReadOnly
                + ", dbIsolation=" + dbIsolation + ", activeConnections=" + activeConnections + "]";
    }
}
```

package com.study.tx.probe;

import java.sql.SQLException;
import java.util.Map;

import javax.sql.DataSource;

import com.zaxxer.hikari.HikariDataSource;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.stereotype.Component;
import org.springframework.transaction.support.TransactionSynchronizationManager;

@Component
public class TxProbe {

    private static final Logger log = LoggerFactory.getLogger(TxProbe.class);

    private static final String SNAPSHOT_SQL =
            "select pg_backend_pid() as pid, "
          + "current_setting('transaction_read_only') as read_only, "
          + "current_setting('transaction_isolation') as isolation";

    private final JdbcTemplate jdbcTemplate;
    private final HikariDataSource hikariDataSource;

    public TxProbe(JdbcTemplate jdbcTemplate, DataSource dataSource) throws SQLException {
        this.jdbcTemplate = jdbcTemplate;
        // active 커넥션 수는 풀만 알고 있다. DataSource가 프록시로 감싸져 있어도 unwrap이 원본 Hikari까지 내려간다.
        this.hikariDataSource = dataSource.unwrap(HikariDataSource.class);
    }

    public TxSnapshot snapshot(String label) {
        // SQL을 먼저 실행하는 순서가 중요하다. 빈 트랜잭션(SUPPORTS 등)은 첫 SQL에서야 커넥션을 빌리므로,
        // active 수를 먼저 읽으면 "이 스코프가 커넥션을 쥐고 있는가"를 관찰할 수 없다.
        Map<String, Object> row = jdbcTemplate.queryForMap(SNAPSHOT_SQL);
        TxSnapshot snapshot = new TxSnapshot(
                label,
                ((Number) row.get("pid")).intValue(),
                TransactionSynchronizationManager.isActualTransactionActive(),
                TransactionSynchronizationManager.getCurrentTransactionName(),
                "on".equals(row.get("read_only")),
                (String) row.get("isolation"),
                activeConnections());
        log.info("{}", snapshot);
        return snapshot;
    }

    public int activeConnections() {
        return hikariDataSource.getHikariPoolMXBean().getActiveConnections();
    }
}

package com.study.tx.support;

import java.util.concurrent.BrokenBarrierException;
import java.util.concurrent.CyclicBarrier;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.TimeoutException;

public final class Barriers {

    private Barriers() {
    }

     * 트랜잭션 메서드 안에서 checked 예외를 노출하지 않기 위한 래퍼.

    public static void await(CyclicBarrier barrier) {
        try {
            barrier.await(5, TimeUnit.SECONDS);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new IllegalStateException("barrier 대기 중 인터럽트", e);
        } catch (BrokenBarrierException | TimeoutException e) {
            throw new IllegalStateException("barrier 실패", e);
        }
    }
}

package com.study.tx.propagation;

import java.util.ArrayList;
import java.util.List;

import com.study.tx.audit.AuditRepository;
import com.study.tx.probe.TxProbe;
import com.study.tx.probe.TxSnapshot;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.dao.DuplicateKeyException;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class OuterService {

    private static final Logger log = LoggerFactory.getLogger(OuterService.class);

    private final InnerService inner;
    private final TxProbe probe;
    private final AuditRepository auditRepository;

    public OuterService(InnerService inner, TxProbe probe, AuditRepository auditRepository) {
        this.inner = inner;
        this.probe = probe;
        this.auditRepository = auditRepository;
    }

    // ---------- 전파와 커넥션 ----------

    @Transactional
    public List<TxSnapshot> requiredCallsRequired() {
        List<TxSnapshot> result = new ArrayList<>();
        result.add(probe.snapshot("outer-REQUIRED"));
        result.add(inner.required());
        return result;
    }

    @Transactional
    public List<TxSnapshot> requiredCallsRequiresNew() {
        List<TxSnapshot> result = new ArrayList<>();
        result.add(probe.snapshot("outer-REQUIRED"));
        result.add(inner.requiresNew());
        return result;
    }

    @Transactional
    public List<TxSnapshot> requiredCallsNotSupported() {
        List<TxSnapshot> result = new ArrayList<>();
        result.add(probe.snapshot("outer-REQUIRED"));
        result.add(inner.notSupported());
        return result;
    }

    // ---------- 옵션은 새 물리 트랜잭션에만 적용 ----------

    @Transactional
    public List<TxSnapshot> requiredCallsSerializable() {
        List<TxSnapshot> result = new ArrayList<>();
        result.add(probe.snapshot("outer-DEFAULT-isolation"));
        result.add(inner.serializable());   // 참여하므로 SERIALIZABLE은 적용되지 않는다
        return result;
    }

    @Transactional(readOnly = true)
    public void readOnlyCallsInsert(String message) {
        inner.insert(message);              // 안쪽은 readOnly=false지만 바깥 read-only 트랜잭션에 참여한다
    }

    // ---------- 롤백 전파 ----------

    @Transactional
    public void rollbackAfterRequiresNew(String message) {
        inner.insertInNewTransaction("audit-" + message);   // 별도 커넥션에서 먼저 커밋된다
        auditRepository.insert("outer-" + message);
        throw new IllegalStateException("outer failed");
    }

    @Transactional
    public void swallowRequiredFailure(String message) {
        auditRepository.insert("outer-" + message);
        try {
            inner.insertThenFail("inner-" + message);
        } catch (IllegalStateException e) {
            log.warn("안쪽 실패를 무시하고 계속 진행: {}", e.getMessage());
        }
    }

    @Transactional
    public void swallowNestedFailure(String message) {
        auditRepository.insert("outer-" + message);
        try {
            inner.insertNestedThenFail("nested-" + message);
        } catch (IllegalStateException e) {
            log.warn("세이브포인트까지만 롤백하고 계속 진행: {}", e.getMessage());
        }
    }

    // ---------- PostgreSQL aborted transaction ----------

    @Transactional
    public void swallowDuplicateKey(String message) {
        auditRepository.insert(message);
        try {
            auditRepository.insert(message);
        } catch (DuplicateKeyException e) {
            log.warn("중복이라 건너뜀 (세이브포인트 없음)");
        }
        auditRepository.insert(message + "-after");
    }

    @Transactional
    public void swallowDuplicateKeyWithSavepoint(String message) {
        auditRepository.insert(message);
        try {
            inner.insertNested(message);
        } catch (DuplicateKeyException e) {
            log.warn("중복이라 건너뜀 (세이브포인트 복구)");
        }
        auditRepository.insert(message + "-after");
    }

package com.study.tx;

import java.sql.SQLException;

import org.springframework.core.NestedExceptionUtils;
import org.springframework.test.context.DynamicPropertyRegistry;
import org.springframework.test.context.DynamicPropertySource;
import org.testcontainers.containers.PostgreSQLContainer;

/**
 * 싱글톤 컨테이너 패턴.
 * @Container로 클래스마다 컨테이너를 재시작하면, Spring이 캐시한 테스트 컨텍스트가 죽은 포트를 가리키게 된다.
 * 프로퍼티가 다른 PoolDeadlockTest는 컨텍스트가 따로 뜨지만 같은 컨테이너를 쓴다.
 */
public abstract class PostgresTestSupport {

    static final PostgreSQLContainer<?> POSTGRES = new PostgreSQLContainer<>("postgres:16-alpine");

    static {
        POSTGRES.start();
    }

    @DynamicPropertySource
    static void datasourceProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", POSTGRES::getJdbcUrl);
        registry.add("spring.datasource.username", POSTGRES::getUsername);
        registry.add("spring.datasource.password", POSTGRES::getPassword);
    }

    /** Spring 예외 번역 결과가 무엇이든 DB가 돌려준 원본 SQLState로 판단한다. */
    protected static String sqlStateOf(Throwable ex) {
        Throwable cause = NestedExceptionUtils.getMostSpecificCause(ex);
        if (cause instanceof SQLException) {
            return ((SQLException) cause).getSQLState();
        }
        return null;
    }
}

### 7.2 `TransactionConnectionTest.java` — 전파·옵션과 커넥션

package com.study.tx;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

import org.springframework.boot.test.context.SpringBootTest;

/**
 * 클래스에 @Transactional을 붙이지 않는다.
 * 테스트 트랜잭션이 열리면 서비스 경계가 모두 "참여"로 바뀌어 관찰하려는 동작 자체가 사라진다.

@SpringBootTest

    @Autowired
    OuterService outer;

    @Autowired
    InnerService inner;

    @Autowired
    TxProbe probe;

    @Autowired
    AuditRepository auditRepository;

    @BeforeEach
    void clean() {
        auditRepository.deleteAll();
    }

    @Test
    @DisplayName("트랜잭션 없음: SQL 직후 커넥션을 반납한다")
    void noTransactionReleasesImmediately() {
        TxSnapshot snapshot = probe.snapshot("no-tx");

        assertThat(snapshot.actualTransactionActive()).isFalse();
        assertThat(snapshot.activeConnections()).isZero();
    }

    @Test
    @DisplayName("REQUIRED → REQUIRED: 같은 물리 커넥션을 공유하고 풀에서 1개만 빌린다")
    void requiredJoinsSameConnection() {
        List<TxSnapshot> snapshots = outer.requiredCallsRequired();
        TxSnapshot outerSnap = snapshots.get(0);
        TxSnapshot innerSnap = snapshots.get(1);

        assertThat(innerSnap.backendPid()).isEqualTo(outerSnap.backendPid());
        assertThat(innerSnap.activeConnections()).isEqualTo(1);
        // 참여는 새 트랜잭션을 만들지 않으므로 ThreadLocal의 트랜잭션 이름도 바깥 것 그대로다
        assertThat(innerSnap.transactionName())
                .isEqualTo(outerSnap.transactionName())
                .endsWith("OuterService.requiredCallsRequired");
    }

    @Test
    @DisplayName("REQUIRED → REQUIRES_NEW: 바깥 커넥션을 반납하지 않은 채 두 번째 커넥션을 빌린다")
    void requiresNewHoldsTwoConnections() {
        List<TxSnapshot> snapshots = outer.requiredCallsRequiresNew();
        TxSnapshot outerSnap = snapshots.get(0);
        TxSnapshot innerSnap = snapshots.get(1);

        assertThat(outerSnap.activeConnections()).isEqualTo(1);
        assertThat(innerSnap.backendPid()).isNotEqualTo(outerSnap.backendPid());
        assertThat(innerSnap.activeConnections()).isEqualTo(2);
        assertThat(innerSnap.transactionName()).endsWith("InnerService.requiresNew");
    }

    @Test
    @DisplayName("REQUIRED → NOT_SUPPORTED: 트랜잭션은 없지만 커넥션은 2개를 쥔다")
    void notSupportedSuspendsButKeepsOuterConnection() {
        List<TxSnapshot> snapshots = outer.requiredCallsNotSupported();
        TxSnapshot outerSnap = snapshots.get(0);
        TxSnapshot innerSnap = snapshots.get(1);

        assertThat(innerSnap.actualTransactionActive()).isFalse();
        assertThat(innerSnap.backendPid()).isNotEqualTo(outerSnap.backendPid());
        assertThat(innerSnap.activeConnections()).isEqualTo(2);
    }

    @Test
    @DisplayName("SUPPORTS(기존 트랜잭션 없음): 물리 트랜잭션은 없지만 스코프 동안 같은 커넥션을 유지한다")
    void supportsWithoutTransactionStillBindsConnection() {
        List<TxSnapshot> snapshots = inner.supportsTwice();
        TxSnapshot first = snapshots.get(0);
        TxSnapshot second = snapshots.get(1);

        assertThat(first.actualTransactionActive()).isFalse();
        assertThat(second.actualTransactionActive()).isFalse();
        assertThat(second.backendPid()).isEqualTo(first.backendPid());
        // 트랜잭션이 없는데도 첫 SQL 이후 반납하지 않고 쥐고 있다 (DataSourceUtils.ConnectionSynchronization)
        assertThat(first.activeConnections()).isEqualTo(1);
        assertThat(second.activeConnections()).isEqualTo(1);
    }

    @Test
    @DisplayName("MANDATORY(기존 트랜잭션 없음): 커넥션을 빌리기 전에 예외")
    void mandatoryWithoutTransactionFails() {

        assertThat(auditRepository.exists("outer-x")).isFalse();
        assertThat(auditRepository.exists("inner-x")).isFalse();

    void postgresAbortsWholeTransactionAfterError() {

    void savepointRecoversPostgresTransaction() {

        assertThat(auditRepository.exists("order-2-paid-PAY-2")).isTrue();

### 7.4 `PoolDeadlockTest.java` — 커넥션 풀 데드락

```java
package com.study.tx;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

import java.util.concurrent.CyclicBarrier;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.TimeUnit;
import java.util.stream.Stream;

import com.study.tx.audit.AuditRepository;
import com.study.tx.deadlock.DeadlockProneService;
import com.study.tx.deadlock.FailureLogFacade;
import com.study.tx.deadlock.MainWorkException;
import org.junit.jupiter.api.AfterEach;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.transaction.CannotCreateTransactionException;

/**
 * 풀 크기 = 동시 스레드 수 = 2 로 맞춰 "모든 스레드가 1개씩 쥐고 1개를 더 기다리는" 상태를 결정적으로 만든다.
 * connection-timeout을 줄여 테스트가 30초 기본값만큼 멈추지 않게 한다 (Hikari 최소값 250ms).
 */
@SpringBootTest(properties = {
        "spring.datasource.hikari.maximum-pool-size=2",
        "spring.datasource.hikari.minimum-idle=2",
        "spring.datasource.hikari.connection-timeout=1000"
})
class PoolDeadlockTest extends PostgresTestSupport {

    @Autowired
    DeadlockProneService deadlockProneService;

    @Autowired
    FailureLogFacade failureLogFacade;

    @Autowired
    AuditRepository auditRepository;

    ExecutorService executor;

    @BeforeEach
    void setUp() {
        auditRepository.deleteAll();
        executor = Executors.newFixedThreadPool(2);
    }

    @AfterEach
    void tearDown() {
        executor.shutdownNow();
    }

    @Test
    @DisplayName("트랜잭션 안에서 REQUIRES_NEW: 풀이 교착되어 최소 한 스레드는 반드시 커넥션 타임아웃")
    void requiresNewInsideTransactionExhaustsPool() throws Exception {
        CyclicBarrier barrier = new CyclicBarrier(2);

        Future<?> first = executor.submit(() -> deadlockProneService.runAndLogFailure(barrier, "a"));
        Future<?> second = executor.submit(() -> deadlockProneService.runAndLogFailure(barrier, "b"));

        Throwable firstFailure = failureOf(first);
        Throwable secondFailure = failureOf(second);

        // 왜 "최소 1개"인가:
        // barrier 이후 두 스레드는 각자 커넥션 1개를 쥔 채 두 번째를 기다린다. 아무도 반납하지 않으므로
        // 먼저 대기를 시작한 스레드는 반드시 타임아웃된다. 그 스레드가 롤백하며 반납한 커넥션을
        // 아직 대기 중인 다른 스레드가 받아 진행할 수 있다(두 대기 시작 시각의 차이에 좌우됨).
        // 운영에서 "타임아웃이 연쇄적으로 풀리며 일부만 실패하는" 모습이 바로 이것이다.
        assertThat(firstFailure).isInstanceOfAny(CannotCreateTransactionException.class, MainWorkException.class);
        assertThat(secondFailure).isInstanceOfAny(CannotCreateTransactionException.class, MainWorkException.class);
        long timeouts = Stream.of(firstFailure, secondFailure)
                .filter(failure -> failure instanceof CannotCreateTransactionException)
                .count();
        assertThat(timeouts).isGreaterThanOrEqualTo(1);

        // 메인 작업은 어느 경우든 롤백되었다
        assertThat(auditRepository.exists("main-a")).isFalse();
        assertThat(auditRepository.exists("main-b")).isFalse();
    }

    @Test
    @DisplayName("메인 트랜잭션 종료 후 로그 트랜잭션: 같은 풀 크기에서 데드락 없이 로그가 남는다")
    void logAfterMainTransactionDoesNotDeadlock() {
        CyclicBarrier barrier = new CyclicBarrier(2);

        Future<?> first = executor.submit(() -> failureLogFacade.runAndLogFailure(barrier, "a"));
        Future<?> second = executor.submit(() -> failureLogFacade.runAndLogFailure(barrier, "b"));

        assertThatThrownBy(() -> first.get(10, TimeUnit.SECONDS))
                .isInstanceOf(ExecutionException.class)
                .hasCauseInstanceOf(MainWorkException.class);
        assertThatThrownBy(() -> second.get(10, TimeUnit.SECONDS))
                .isInstanceOf(ExecutionException.class)
                .hasCauseInstanceOf(MainWorkException.class);

        assertThat(auditRepository.exists("failed-a")).isTrue();
        assertThat(auditRepository.exists("failed-b")).isTrue();
        assertThat(auditRepository.exists("main-a")).isFalse();
        assertThat(auditRepository.exists("main-b")).isFalse();
    }

    private static Throwable failureOf(Future<?> future) throws Exception {
        try {
            future.get(10, TimeUnit.SECONDS);
            return null;
        } catch (ExecutionException e) {
            return e.getCause();
        }
    }
}
```

> Java 8 코드베이스로 옮길 때: Spring Boot 3는 Java 17+가 필요하므로 Spring 4.x/5.x + `@ContextConfiguration` 기반으로 바꾸고, `record` 접근자(`backendPid()`)를 `getBackendPid()`로 바꾼다. DB는 H2로 대체하지 말고 실제 PostgreSQL을 쓴다. H2에는 PostgreSQL의 aborted transaction(`25P02`) 동작이 없어 7.3의 해당 테스트를 재현할 수 없다.

### 변형 1 — `LazyConnectionDataSourceProxy`로 감싸면 커넥션 수가 어떻게 바뀔까?

`OuterService`에 SQL을 실행하지 않고 곧바로 `REQUIRES_NEW`를 호출하는 메서드를 추가한다.

```java
@Transactional
public TxSnapshot requiresNewWithoutOuterSql() {
    return inner.requiresNew();
}
```

그리고 아래 설정을 추가한다.

```java
package com.study.tx.config;

import javax.sql.DataSource;

import com.zaxxer.hikari.HikariDataSource;
import org.springframework.boot.autoconfigure.jdbc.DataSourceProperties;
import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Primary;
import org.springframework.jdbc.datasource.LazyConnectionDataSourceProxy;

@Configuration
public class LazyDataSourceConfig {

    // DataSource 빈을 직접 정의하면 Boot의 Hikari 자동 구성이 물러나므로 원본 풀도 직접 만든다
    @Bean
    @ConfigurationProperties("spring.datasource.hikari")
    public HikariDataSource hikariDataSource(DataSourceProperties properties) {
        return properties.initializeDataSourceBuilder().type(HikariDataSource.class).build();
    }

    // @Primary: 트랜잭션 매니저·JdbcTemplate·schema 초기화가 모두 "같은 인스턴스"를 받아야 리소스 키가 일치한다
    @Bean
    @Primary
    public DataSource dataSource(HikariDataSource hikariDataSource) {
        return new LazyConnectionDataSourceProxy(hikariDataSource);
    }
}
```

**질문**
1. `requiresNewWithoutOuterSql()` 안쪽 스냅샷의 `activeConnections`는 1인가 2인가?
2. `TxConfig`의 `enforceReadOnly=true`를 유지하면 `readOnly` 트랜잭션에서 지연 획득 효과가 유지되는가?
3. `@Primary`를 빼고 `JdbcTemplate`만 `hikariDataSource`를 받도록 바꾸면 `TransactionPitfallTest`의 어떤 테스트가 깨지는가?

<details>
<summary>예상 결과</summary>

1. **1**. 바깥 트랜잭션의 `doBegin`은 프록시 커넥션만 만들고 물리 커넥션은 빌리지 않는다(`getAutoCommit`/`setAutoCommit`은 프록시가 기록만 함). 바깥이 SQL을 실행하지 않았으므로 suspend된 것은 "빈 프록시"이고, 안쪽 SQL이 첫 물리 커넥션을 빌린다. 단 `LazyConnectionDataSourceProxy`는 기본 autocommit/격리 수준을 알기 위해 최초 1회 커넥션을 조회할 수 있다.
2. **유지되지 않는다.** `prepareTransactionalConnection`이 `SET TRANSACTION READ ONLY`를 `Statement`로 실행하므로 `doBegin` 시점에 물리 커넥션을 빌린다. 읽기 전용 라우팅 목적이라면 `enforceReadOnly`와 조합을 확인해야 한다.
3. `requiresNewSurvivesOuterRollback`, `swallowedParticipatingFailureCausesUnexpectedRollback`, `nestedFailureRollsBackOnlyToSavepoint`, `postgresAbortsWholeTransactionAfterError` 등. 트랜잭션 매니저는 프록시 인스턴스를 키로 바인딩하는데 `JdbcTemplate`은 원본 Hikari를 키로 조회하므로, 모든 SQL이 autocommit 커넥션에서 즉시 커밋된다(이론 8.12).
</details>

### 변형 2 — 스레드 4개로 늘리면 풀 크기는 몇이어야 할까?

`PoolDeadlockTest`의 `requiresNewInsideTransactionExhaustsPool`을 복사해 `Executors.newFixedThreadPool(4)`, `new CyclicBarrier(4)`, 스레드 4개 제출로 바꾼다.

**질문**
1. `maximum-pool-size=4`면 결과는?
2. HikariCP 공식 `Tn × (Cm − 1) + 1`로 계산한 최소 풀 크기는? 그 값으로 바꾸면 결과는?
3. 풀 크기를 그 값으로 두고 `CyclicBarrier`를 제거하면 "운 좋게" 통과하는 경우가 생기는 이유는?

<details>
<summary>예상 결과</summary>

1. 4개 스레드가 바깥 커넥션 4개를 모두 쥔 뒤 barrier를 통과하므로 풀이 교착된다. 가장 먼저 대기한 스레드는 반드시 `CannotCreateTransactionException`, 이후 스레드는 앞선 실패자가 반납한 커넥션을 타임아웃 전에 받느냐에 따라 성공/실패가 갈린다. 모든 요청이 최소 `connection-timeout`만큼 지연된다.
2. `Tn = 4`, `Cm = 2` → `4 × 1 + 1 = 5`. 여분 1개를 한 스레드가 받아 안쪽 트랜잭션을 끝내고 반납하면, 그 스레드의 바깥 트랜잭션도 끝나 커넥션 2개가 풀로 돌아온다. 이 연쇄로 전원이 `connection-timeout` 안에 완료되고 `MainWorkException`만 전달된다. 로그 `failed-a~d`가 남는다.
3. barrier가 없으면 스레드들이 바깥 커넥션을 동시에 쥐는 순간이 보장되지 않아, 먼저 끝난 스레드가 반납한 커넥션으로 다음 스레드가 진행할 수 있다. 운영에서 "평소엔 괜찮다가 트래픽 피크에만 멈추는" 이유와 같다.
</details>

### 변형 3 — JPA로 바꾸면 무엇이 달라질까?

1. `spring-boot-starter-jdbc`를 `spring-boot-starter-data-jpa`로 바꾼다.
2. `TxConfig`를 **삭제**한다. 남겨두면 `JdbcTransactionManager`가 우선하여 JPA `EntityManager`가 트랜잭션에 참여하지 않는다.
3. `application.yml`에 `spring.jpa.open-in-view: false`를 넣고, 이어서 아래 두 설정을 넣었을 때와 뺐을 때를 비교한다.

```yaml
spring:
  datasource:
    hikari:
      auto-commit: false
  jpa:
    open-in-view: false
    properties:
      hibernate.connection.provider_disables_autocommit: true
```

**질문**
1. `TransactionConnectionTest`의 PID/active 커넥션 단언은 그대로 통과하는가? (`JdbcTemplate`이 JPA 트랜잭션에 참여하는 경로는?)
2. `nestedFailureRollsBackOnlyToSavepoint`는 어떻게 되는가?
3. `requiresNewWithoutOuterSql()`(변형 1의 메서드)에서 `provider_disables_autocommit` 설정 유무에 따라 안쪽 `activeConnections`가 달라지는가? `@Transactional(readOnly = true)`를 바깥에 붙이면?

<details>
<summary>예상 결과</summary>

1. 대부분 통과할 것으로 예상한다. `JpaTransactionManager`가 `EntityManagerFactoryInfo`에서 `DataSource`를 감지해 `ConnectionHolder`를 `DataSource` 키로도 바인딩하므로 `JdbcTemplate`이 같은 커넥션을 쓴다. 단 `enforceReadOnly`가 없어지므로 `readOnly` 관련 단언은 PgJDBC의 `setReadOnly` 동작(`readOnlyMode`)에 의존하게 된다 — 확인 필요.
2. `NestedTransactionNotSupportedException`으로 실패할 것으로 예상한다(`HibernateJpaDialect`가 JPA 세이브포인트를 제공하지 않음 — Spring 6.2 기준 확인 필요).
3. 설정이 없으면 Hibernate `begin()`이 autocommit 확인·해제를 위해 물리 커넥션을 빌리므로 바깥이 SQL을 실행하지 않아도 안쪽은 2. 설정을 넣으면 첫 SQL까지 지연되어 1이 될 수 있다. 바깥에 `readOnly = true`를 붙이면 `HibernateJpaDialect#beginTransaction`이 `setReadOnly`를 위해 커넥션을 준비하므로 다시 2가 될 것으로 예상한다. 이 세 가지는 이론 4.7 표의 JPA 행을 직접 검증하는 실험이다.
</details>
