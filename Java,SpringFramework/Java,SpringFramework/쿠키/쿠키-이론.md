# 쿠키 (HTTP Cookie)

관련 문서: [예제](./쿠키-예제.md) · [세션](../세션/세션-이론.md) · [분산 세션](../분산세션/분산세션-이론.md) · [HTTP](../../../Network/네트워크 기초/05-HTTP-이론.md) · [TLS](../../../Network/네트워크 기초/06-TLS-이론.md) · [프록시](../프록시/프록시-이론.md)

> 이 문서는 **브라우저가 쿠키를 저장하고 다시 보내는 규칙**을 다룬다. 서버가 쿠키 값(`JSESSIONID`)으로 사용자 상태를 찾는 과정은 [세션](../세션/세션-이론.md) 문서에서 다룬다.

---

## 1. 한 줄 요약

서버가 응답으로 작은 문자열을 브라우저에 맡겨두면, 브라우저가 조건이 맞는 다음 요청마다 그 문자열을 자동으로 되돌려 보내는 방식이다.
정확히는 `Set-Cookie` 응답 헤더로 저장되고 `Cookie` 요청 헤더로 전송되는 이름=값 쌍이며, **어느 요청에 실을지는 전적으로 브라우저가 속성(Domain, Path, Secure, SameSite 등)을 보고 결정**하는 HTTP 상태 관리 메커니즘(RFC 6265)이다.

---

## 2. 왜 필요한가

HTTP는 **무상태(stateless)** 프로토콜이다. 서버 입장에서 두 번째 요청이 첫 번째 요청과 같은 사용자에게서 왔는지 알 방법이 프로토콜에 없다.

쿠키 이전의 해법과 한계는 다음과 같다.


| 기존 해법                                             | 한계                                                                |
| ------------------------------------------------- | ----------------------------------------------------------------- |
| URL에 식별자 붙이기 (`/cart?uid=123`, `;jsessionid=...`) | 링크를 공유하면 식별자도 같이 새어 나간다. 모든 링크를 서버가 다시 써야 한다. 로그·Referer 헤더로 유출된다 |
| 폼의 hidden 필드                                      | POST 폼 이동에서만 유지된다. 일반 링크 클릭, 새 탭에서는 끊긴다                           |
| 클라이언트 IP로 식별                                      | NAT·프록시 뒤의 여러 사용자가 같은 IP를 쓴다. 모바일은 IP가 수시로 바뀐다                    |


쿠키는 이 문제를 **"브라우저가 알아서 붙여 보낸다"**로 풀었다. 개발자가 링크마다 식별자를 붙일 필요가 없다.
그 대가로 생긴 문제가 있다. 브라우저가 *알아서* 보내기 때문에 **사용자가 의도하지 않은 요청에도 쿠키가 실린다**(CSRF). 그래서 이후 15년간 쿠키 스펙의 변화는 대부분 "언제 보내지 말아야 하는가"를 추가하는 방향이었다. (HttpOnly → Secure 강화 → SameSite → 서드파티 쿠키 차단)

## 3. 최소 예제로 보기

```java
@RestController
class CookieDemoController {

    @GetMapping("/set")
    ResponseEntity<Void> set() {
        ResponseCookie cookie = ResponseCookie.from("theme", "dark")
                .path("/")
                .maxAge(Duration.ofDays(7))
                .httpOnly(true)
                .sameSite("Lax")
                .build();
        return ResponseEntity.ok()
                .header(HttpHeaders.SET_COOKIE, cookie.toString())
                .build();
    }

    @GetMapping("/read")
    String read(@CookieValue(name = "theme", required = false) String theme) {
        return "theme=" + theme;
    }
}
```

```text
# 1) 첫 요청 — 서버가 저장을 "부탁"한다
GET /set
→ HTTP/1.1 200
  Set-Cookie: theme=dark; Path=/; Max-Age=604800; Expires=Wed, 26 Nov 2026 ...; HttpOnly; SameSite=Lax

# 2) 이후 요청 — 브라우저가 "자동으로" 붙인다. 속성은 돌아오지 않는다
GET /read
  Cookie: theme=dark
→ theme=dark
```

여기서 봐야 할 점은 두 가지다.

1. 서버는 저장해 달라고 **요청만** 한다. 저장할지, 언제 보낼지는 브라우저가 결정한다.
2. 돌아오는 `Cookie` 헤더에는 **이름=값만** 있다. Path, Max-Age, HttpOnly 같은 속성은 서버로 돌아오지 않는다. 서버는 받은 쿠키가 언제 만료되는지, 어느 Path로 저장됐는지 모른다.

## 4. 핵심 개념


| 용어           | 영문                        | 의미                                                                                                  |
| ------------ | ------------------------- | --------------------------------------------------------------------------------------------------- |
| 쿠키 저장소       | Cookie Store / Cookie Jar | 브라우저가 쿠키를 보관하는 곳. 쿠키는 **(이름, Domain, Path)** 세 값으로 구분된다                                             |
| 호스트 전용 쿠키    | Host-only Cookie          | `Domain` 속성 없이 저장된 쿠키. 저장한 호스트에만 정확히 일치할 때 전송된다                                                     |
| 세션 쿠키        | Session Cookie            | `Max-Age`/`Expires`가 없는 쿠키. 브라우저 세션이 끝나면 지워진다. 서버의 HttpSession과는 다른 개념이다                            |
| 영속 쿠키        | Persistent Cookie         | 만료 시각이 지정된 쿠키. 브라우저를 껐다 켜도 남는다                                                                      |
| 사이트          | Site                      | 스킴 + 등록 가능 도메인(eTLD+1). `https://a.example.com`과 `https://b.example.com`은 같은 사이트다. **포트는 포함되지 않는다** |
| 오리진          | Origin                    | 스킴 + 호스트 + 포트. CORS의 기준이다. 사이트보다 좁다                                                                 |
| 퍼스트파티 / 서드파티 | First-party / Third-party | 주소창의 사이트와 같은 사이트의 쿠키 / 다른 사이트의 쿠키                                                                   |
| 쿠키 접두어       | Cookie Prefix             | `__Host-`, `__Secure-`로 시작하는 이름. 브라우저가 속성 조건을 강제한다                                                  |

## 5. 동작 원리와 흐름

### 5.1 저장 (Set-Cookie 수신)

1. 서버가 응답에 `Set-Cookie` 헤더를 **쿠키 하나당 한 줄** 넣는다. (다른 헤더처럼 쉼표로 합칠 수 없다. `Expires` 날짜에 쉼표가 들어가기 때문이다)
2. 브라우저가 헤더를 파싱해 이름, 값, 속성을 꺼낸다.
3. 거부 조건을 검사한다. 하나라도 걸리면 **아무 에러 없이 버린다.**
   - `Domain`이 현재 호스트를 포함하지 않는다. (예: `api.example.com`이 `Domain=other.com` 지정)
     - 다른사이트의 쿠키를 만들려고하면 거부한다. 응답한 서버가 api.example.com이면 [example.com](http://example.com) 가능. [other.com](http://other.com) 거부.
   - `Domain`이 공개 접미사(public suffix, 예: `co.kr`, `github.io`)다.
     - [`co.kr`](http://co.kr) 아래에는 서로 관계없는 여러 사이트가 있기 때문에 **여러 독립적인 사이트가 공유하는 접미사**를 쿠키의 Domain으로 지정하지 못하게 한다.
   - `SameSite=None`인데 `Secure`가 없다.
     - **SameSite : 다른 사이트에서 내 사이트로 요청이 발생할 때, 쿠키를 함께 보낼지 정하는 속성**. 
     - 로그인한 [`bank.com`](http://bank.com)의 쿠키가 브라우저에 있다고 해볼게요. 다른 사이트인 [`other.com`](http://other.com)에서 [`bank.com`](http://bank.com)으로 요청을 보내면, `SameSite` 설정에 따라 쿠키 전송 여부가 달라진다.
     - Strict : 쿠키를 보내지 않음
     - Lax : 링크를 눌러 페이지를 여는 일반적인 GET 이동에는 보낸다. 다른 사이트 안의 이미지/iframe/post 요청은 보내지 않는다.
     - None : 다른 사이트에서 발생한 요청에도 전송을 허용. Secure 필수.
   - `Secure` 쿠키를 HTTP(비보안) 페이지가 저장하려 한다. (localhost는 브라우저가 예외로 둔다. 확인 필요: 브라우저별 차이)
   - `__Host-` 접두어인데 `Secure`, `Path=/`, `Domain` 없음 조건을 만족하지 않는다.
   - 서드파티 문맥이고 브라우저가 서드파티 쿠키를 차단 중이다.
4. 저장소에서 **(이름, Domain, Path)가 같은** 쿠키를 찾아 덮어쓴다. 셋 중 하나라도 다르면 **별개의 쿠키로 추가**된다.
   - `Secure`**는 쿠키를 HTTPS 연결에서만 서버로 보내도록 하는 속성**
5. `Max-Age=0`이거나 `Expires`가 과거면 같은 키의 쿠키를 **삭제**한다. 삭제 명령도 4번과 같은 키로 찾는다.

### 5.2 전송 (요청 생성)

브라우저가 요청을 만들 때마다 저장소의 모든 쿠키에 대해 다음을 검사한다.

1. **도메인 일치**: 호스트 전용 쿠키는 호스트가 정확히 같아야 한다. `Domain=example.com` 쿠키는 `example.com`과 모든 하위 도메인에 전송된다.
2. **경로 일치**: 요청 경로가 쿠키 `Path`로 시작해야 한다. (`Path=/api` → `/api`, `/api/users` 전송, `/apix`는 미전송)
3. **Secure**: `Secure` 쿠키는 HTTPS 요청에만 싣는다.
4. **SameSite**: 요청이 cross-site면 아래 표에 따라 뺀다.
5. **만료**: 만료된 쿠키는 버린다.
6. **CORS 자격 증명 모드**: JavaScript `fetch`/XHR이 다른 **오리진**으로 보내는 요청은 `credentials: 'include'`(axios는 `withCredentials: true`)가 없으면 쿠키를 싣지 않는다.
7. 통과한 쿠키를 `Cookie: a=1; b=2` 한 줄로 합친다. Path가 긴 쿠키가 앞에 온다.


| SameSite            | cross-site 하위 요청 (img, iframe, fetch)                 | cross-site 최상위 GET 이동 (링크 클릭) | cross-site 최상위 POST (폼 전송) |
| ------------------- | ----------------------------------------------------- | ----------------------------- | -------------------------- |
| `Strict`            | 미전송                                                   | **미전송**                       | 미전송                        |
| `Lax`               | 미전송                                                   | 전송                            | 미전송                        |
| `None` (+Secure 필수) | 전송                                                    | 전송                            | 전송                         |
| 속성 생략               | 브라우저마다 다름. Chrome·Edge는 `Lax`로 취급 (Chrome 80, 2020\~) |                               |                            |


> Chrome은 SameSite를 생략한 쿠키에 한해 "생성 후 2분 이내면 최상위 POST에도 전송"하는 임시 예외(Lax+POST)를 두었다. 남아 있는지는 확인 필요. 이 예외에 기대지 말고 SameSite를 명시한다.

```mermaid
sequenceDiagram
    participant B as 브라우저<br/>(쿠키 저장소)
    participant S as 서버<br/>(Spring MVC)

    B->>S: GET /login (쿠키 없음)
    S-->>B: 200 + Set-Cookie: sid=abc; Path=/; HttpOnly; Secure; SameSite=Lax
    Note over B: 거부 조건 검사<br/>(이름,Domain,Path) 키로 저장

    B->>S: GET /orders<br/>Cookie: sid=abc
    Note over B: 도메인·경로·Secure·SameSite·만료<br/>검사를 통과한 쿠키만 첨부
    S-->>B: 200

    Note over B: evil.com 페이지에서<br/>POST https://our.com/transfer 폼 전송
    B->>S: POST /transfer (sid 미첨부: SameSite=Lax)
    S-->>B: 401 / 403
```

### 5.3 계층별로 생기는 객체


| 계층                | 객체                            | 생명 주기                                                   |
| ----------------- | ----------------------------- | ------------------------------------------------------- |
| 브라우저              | 쿠키 저장소의 항목                    | 만료 시각까지. 세션 쿠키는 브라우저 종료까지 (단, "이전 탭 복원" 설정 시 살아남을 수 있다) |

## 6. 내부 구현 (핵심만)

### 6.1 서버로 돌아오는 것은 "이름=값"뿐이다

`HttpServletRequest#getCookies()`가 돌려주는 `Cookie` 객체의 `getMaxAge()`, `getPath()`, `getDomain()`은 **항상 기본값**(-1, null)이다. 브라우저가 속성을 보내지 않으니 컨테이너도 채울 수 없다.
그래서 "읽은 쿠키를 그대로 `addCookie`로 다시 보내서 갱신·삭제"하면 Path가 비어 있는 **다른 키의 쿠키**가 생긴다. (→ 함정 3)

### 6.2 Tomcat의 `Rfc6265CookieProcessor`가 값을 검사한다

Tomcat 8.5부터 기본 쿠키 처리기는 `Rfc6265CookieProcessor`다. `Set-Cookie`를 만들 때 값에 **공백, 쉼표, 세미콜론, 큰따옴표, 역슬래시, 비 ASCII 문자(한글 등)**가 있으면 `IllegalArgumentException`을 던진다. 서버 쪽 예외이므로 응답은 500이 된다.
쿠키 헤더 문법(RFC 6265의 `cookie-octet`)이 이 문자들을 허용하지 않기 때문이다. 한글·JSON을 넣으려면 Base64URL이나 URL 인코딩을 거쳐야 한다. (→ 함정 4)

> MockMvc의 `MockHttpServletResponse`는 이 검사를 하지 않는다. **MockMvc 테스트는 통과하고 실제 Tomcat에서 500이 나는** 경로가 여기서 생긴다.

### 6.3 SameSite는 `Cookie` 클래스에 늦게 들어왔다

`jakarta.servlet.http.Cookie`에는 Servlet 6.0(Jakarta EE 10, Tomcat 10.1, **Spring Boot 3.x**) 전까지 SameSite를 지정할 메서드가 없었다. Servlet 6.0에서 `Cookie#setAttribute(String, String)`이 추가되어 `cookie.setAttribute("SameSite", "Lax")`가 가능해졌다.
Spring은 이 공백을 `org.springframework.http.ResponseCookie`(Spring 5.0+)로 메워 왔다. `ResponseCookie#toString()`은 완성된 `Set-Cookie` 헤더 값을 만들고, 이를 `HttpHeaders.SET_COOKIE`로 직접 넣으므로 서블릿 버전과 관계없이 SameSite를 붙일 수 있다.

### 6.4 HttpOnly는 "읽기"만 막는다

`HttpOnly` 쿠키는 `document.cookie`로 읽을 수 없다. XSS로 주입된 스크립트가 세션 ID를 **훔쳐 가는 것**을 막는다.
그러나 브라우저가 요청에 **자동 첨부하는 것**은 막지 않는다. XSS 스크립트가 `fetch('/api/transfer', {method:'POST'})`를 호출하면 쿠키는 그대로 실린다. HttpOnly는 CSRF 방어가 아니다. (→ 함정 5)

### 6.5 CORS의 자격 증명 모드가 SameSite와 별개로 동작한다

`localhost:3000`(React 개발 서버)과 `localhost:8080`(Spring)은 **포트만 달라서 같은 사이트지만 다른 오리진**이다.
SameSite 검사는 통과하지만, `fetch`는 cross-origin 요청에 기본값 `credentials: 'same-origin'`을 쓰므로 쿠키를 빼고 보낸다. 서버도 `Access-Control-Allow-Credentials: true`와 **와일드카드가 아닌** `Access-Control-Allow-Origin`을 응답해야 브라우저가 응답과 `Set-Cookie`를 받아들인다. (→ 함정 1)

## 7. 유사 개념과의 비교


| 항목        | 쿠키              | `localStorage`        | `sessionStorage` | 서버 세션         |
| --------- | --------------- | --------------------- | ---------------- | ------------- |
| 저장 위치     | 브라우저            | 브라우저                  | 브라우저 (탭 단위)      | 서버 (쿠키에는 ID만) |
| 요청에 자동 첨부 | **예**           | 아니요 (JS가 헤더에 직접 넣음)   | 아니요              | 쿠키를 통해 간접     |
| JS 접근     | HttpOnly면 불가    | 항상 가능                 | 항상 가능            | 불가            |
| 크기        | 쿠키당 약 4KB       | 오리진당 약 5MB (브라우저별 상이) | 약 5MB            | 서버 메모리/저장소 한도 |
| 만료        | Max-Age/Expires | 없음 (직접 삭제)            | 탭 닫으면 삭제         | 서버 타임아웃       |
| 주 위협      | CSRF            | XSS로 탈취               | XSS로 탈취          | 세션 고정, 하이재킹   |


**선택 기준**

- 인증 토큰(세션 ID, JWT 포함)은 **HttpOnly + Secure + SameSite 쿠키**에 둔다. `localStorage`에 둔 토큰은 XSS 한 번에 외부로 유출된다. 쿠키 방식은 XSS가 있어도 토큰 *값*은 유출되지 않는다. (대신 CSRF를 막아야 한다)
- 크고 민감하지 않은 UI 상태(필터, 초안)는 `localStorage`. 쿠키에 넣으면 모든 요청에 실려 대역폭을 먹는다.
- 바꾸면 안 되는 값(권한, 가격, 사용자 ID)은 쿠키 **값**으로 두지 않는다. 서버 세션에 두고 쿠키에는 추측 불가능한 ID만 둔다. 쿠키에 꼭 두어야 하면 서명(HMAC)한다.

## 8. 함정과 안티패턴

### 함정 1. React → Spring 호출에서 쿠키가 안 실리거나 저장되지 않는다

- **증상**: Postman에서는 로그인이 유지되는데 브라우저(React)에서는 매 요청이 비로그인. 개발자 도구에 `Set-Cookie`는 보이는데 저장소에 없다.
- **원인**: 5.2-6번, 6.5. 다른 오리진으로 가는 `fetch`는 `credentials: 'include'`가 없으면 쿠키를 보내지도, 응답의 `Set-Cookie`를 저장하지도 않는다. 서버가 `Allow-Origin: *`이면 자격 증명 요청은 브라우저가 거부한다.
- **해결**: 프론트 `fetch(url, {credentials: 'include'})` 또는 `axios.defaults.withCredentials = true`. 서버는 `allowedOrigins("http://localhost:3000")` + `allowCredentials(true)`. 운영에서는 같은 오리진(리버스 프록시로 `/api` 경로 분기)으로 묶으면 이 문제 자체가 사라진다. ([프록시](../프록시/프록시-이론.md))

### 함정 2. 서드파티 연동(결제창, iframe, OAuth 콜백 POST) 후 로그인이 풀린다

- **증상**: PG사 결제창이 우리 서버로 **POST** 콜백을 보낸 직후 세션이 없어서 결제 완료 페이지가 로그인 페이지로 튄다. Chrome 80 이후 갑자기 발생한 경우가 많다.
- **원인**: 5.2 표. SameSite 속성이 없는 쿠키를 Chrome은 `Lax`로 취급하고, `Lax`는 cross-site **POST** 최상위 이동에 쿠키를 싣지 않는다.
- **해결**: 콜백 흐름에 필요한 쿠키만 `SameSite=None; Secure`로 명시한다. 세션 쿠키 전체를 None으로 풀면 CSRF 위험이 커지므로, 가능하면 콜백은 세션에 의존하지 않고 주문 번호 + 서명 검증으로 처리한다. 반대로 `SameSite=None`인데 `Secure`를 빼면 쿠키가 **조용히 버려진다**(5.1-3).

### 함정 3. 쿠키를 지웠는데 안 지워진다 / 같은 이름 쿠키가 두 개 실린다

- **증상**: 로그아웃 API가 `Max-Age=0`을 내려도 쿠키가 남는다. 서버 로그에 `Cookie: token=old; token=new`가 찍힌다.
- **원인**: 5.1-4, 6.1. 쿠키 키는 (이름, Domain, Path)다. 저장할 때 `Path=/api`로 넣고 지울 때 Path를 생략하면(기본값은 현재 요청 경로의 디렉터리) 다른 키라서 지워지지 않는다. 또 `request.getCookies()`로 읽은 객체는 Path가 null이라 그대로 `setMaxAge(0)` 해도 같은 문제가 난다.
- **해결**: 쿠키 생성·삭제를 한 곳(유틸/컴포넌트)에 모아 **같은 Domain/Path 상수**를 쓴다. 저장과 삭제 모두 `Path=/`로 통일하는 것이 가장 단순하다.

### 함정 4. 쿠키에 한글·JSON을 넣으면 운영에서만 500

- **증상**: 로컬 MockMvc 테스트는 통과하는데 실제 서버에서 `IllegalArgumentException: An invalid character [...] was present in the Cookie value`.
- **원인**: 6.2. Tomcat `Rfc6265CookieProcessor`가 비 ASCII·공백·쉼표·따옴표를 거부한다. MockMvc는 이 검사를 하지 않는다.
- **해결**: `Base64.getUrlEncoder().withoutPadding()` 또는 `URLEncoder.encode(value, UTF_8)`로 인코딩한다. 애초에 쿠키에는 ID 같은 짧은 ASCII만 두고, 데이터는 서버에 둔다.

### 함정 5. HttpOnly만 켜면 안전하다고 생각한다

- **증상**: 보안 점검에서 CSRF 취약점 지적. "HttpOnly 쿠키인데 왜?"
- **원인**: 6.4. HttpOnly는 JS가 값을 **읽는 것**만 막는다. 브라우저의 자동 첨부(5.2)는 그대로이므로, 다른 사이트의 폼이나 XSS 스크립트가 보낸 요청에도 쿠키가 실린다.
- **해결**: `SameSite=Lax` 이상 + CSRF 토큰(Spring Security 기본 활성). 상태 변경은 GET으로 만들지 않는다(`Lax`는 최상위 GET을 허용하므로).

### 함정 6. `Domain=example.com`을 습관적으로 붙인다

- **증상**: 하위 서비스(`blog.example.com`, 외부 업체가 운영하는 `event.example.com`)에서 메인 서비스의 인증 쿠키를 받는다. 하위 도메인 하나가 XSS에 뚫리면 메인 세션 쿠키를 **덮어쓸** 수도 있다(쿠키 토싱, cookie tossing).
- **원인**: 5.2-1. Domain을 명시하면 모든 하위 도메인으로 범위가 넓어진다. 생략해야 호스트 전용이 된다.
- **해결**: 하위 도메인 공유가 필요 없으면 `Domain`을 생략한다. 인증 쿠키는 `__Host-` 접두어로 Domain 지정 자체를 브라우저가 거부하게 만든다.

### 함정 7. TLS 종료 프록시 뒤에서 Secure가 안 붙는다

- **증상**: 운영은 HTTPS인데 Spring이 만든 세션 쿠키에 `Secure`가 없다. 또는 `request.isSecure()`로 분기한 코드가 항상 false.
- **원인**: Nginx/ALB가 HTTPS를 풀고 Tomcat에는 HTTP로 넘기므로, Tomcat은 HTTP 요청으로 인식한다. Tomcat은 요청이 secure일 때만 세션 쿠키에 Secure를 자동으로 붙인다.
- **해결**: `server.forward-headers-strategy=native`(또는 `framework`)로 `X-Forwarded-Proto`를 신뢰하게 하거나, `server.servlet.session.cookie.secure=true`로 고정한다. 앱이 직접 만드는 쿠키는 항상 `secure(true)`를 명시한다.

## 11. 자가 점검 질문

1. 서버가 `Set-Cookie: a=1; Path=/api`로 쿠키를 저장했다. `POST /auth/logout` 응답에서 `Set-Cookie: a=; Max-Age=0`을 보냈는데 쿠키가 지워지지 않는 이유는?
2. React 개발 서버 `http://localhost:3000`에서 `http://localhost:8080/api/me`를 `fetch`로 호출한다. SameSite 때문에 쿠키가 빠지는가? 쿠키가 빠진다면 무엇 때문인가?
3. `SameSite=Lax` 세션 쿠키를 쓰는 서비스에 `GET /account/delete` API가 있다. 어떤 공격이 가능한가?
4. HttpOnly 쿠키가 XSS에서 막아주는 것과 막아주지 못하는 것은?
5. 로컬 MockMvc 테스트에서는 성공하던 `response.addCookie(new Cookie("name", "홍길동"))`이 운영 서버에서 500을 내는 이유는?

<details>
<summary>답</summary>

1. 쿠키는 (이름, Domain, Path)로 구분된다. Path를 생략한 명령은 기본 Path(요청 경로의 마지막 `/` 앞까지, 여기서는 `/auth`)를 키로 삼으므로 `Path=/api` 쿠키와 다른 키다. 그래서 기존 쿠키는 남고, 삭제 명령은 존재하지 않는 `(a, 호스트, /auth)` 쿠키를 지우려다 아무 일도 하지 않는다. 삭제할 때도 `Path=/api`를 명시해야 한다.
2. 빠지지 않는다. 사이트는 스킴 + eTLD+1이고 포트를 포함하지 않으므로 둘은 same-site다. 대신 오리진(포트 포함)이 달라 CORS 자격 증명 규칙이 적용된다. `credentials: 'include'`가 없으면 쿠키를 싣지 않고, 서버가 `Allow-Credentials: true`와 구체적인 `Allow-Origin`을 주지 않으면 응답을 거부한다.
3. `Lax`는 cross-site **최상위 GET 이동**에 쿠키를 싣는다. 공격자 사이트의 `<a href="https://our.com/account/delete">` 클릭(또는 `location.href` 이동)만으로 로그인한 사용자 계정이 삭제된다. 상태 변경은 GET으로 만들지 않아야 한다.
4. 막는 것: `document.cookie`로 값을 읽어 외부로 빼돌리는 것. 막지 못하는 것: XSS 스크립트가 같은 오리진으로 요청을 보낼 때 브라우저가 쿠키를 자동 첨부하는 것. 즉 세션 ID 탈취는 막지만, 탈취 없이 사용자 권한으로 행동하는 것은 막지 못한다.
5. Tomcat 8.5+의 `Rfc6265CookieProcessor`가 `Set-Cookie` 생성 시 비 ASCII 문자를 거부해 `IllegalArgumentException`을 던진다. MockMvc의 `MockHttpServletResponse`는 이 검사를 하지 않는다. Base64URL·URL 인코딩을 적용해야 한다.

</details>
