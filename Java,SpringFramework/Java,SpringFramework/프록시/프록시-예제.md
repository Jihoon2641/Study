# 프록시 예제

관련 문서: [이론](./프록시-이론.md)

---

## 1. 예제 개요

두 부분으로 나눈다.

- **Part A — 순수 Java**: JDK 내장 `HttpServer`로 원본 서버·포워드 프록시·리버스 프록시를 직접 만들고, 원본 서버가 "누가 연결했는지"를 출력한다. 외부 의존성 없음.
- **Part B — Spring Boot**: 리버스 프록시 뒤에서 `getRemoteAddr()`·`getScheme()`·URL 생성이 어떻게 틀어지는지, `ForwardedHeaderFilter`(framework 전략)와 Tomcat `RemoteIpFilter`(native 전략과 같은 로직)가 어떻게 다르게 고치는지 테스트로 증명한다.

| 예제 | 검증하는 개념 | 이론 문서 대응 |
|---|---|---|
| A-1 직접 호출 | 기준선: 프록시 없음 | 3장 |
| A-2 포워드 프록시 경유 | 클라이언트가 프록시를 설정, absolute-form 요청 | 5.2 |
| A-3 리버스 프록시 경유 | 클라이언트는 프록시 주소만 앎, 프록시가 라우팅 | 5.4 |
| A-4 XFF 위조 | 맨 왼쪽 값은 클라이언트가 쓸 수 있음 | 6.3, 함정 3 |
| B-1 헤더 해석 없음 | `none` 전략: remoteAddr=프록시, scheme=http | 6.2, 함정 1·2 |
| B-2 `ForwardedHeaderFilter` | `framework` 전략: 헤더 무조건 신뢰, XFF 맨 왼쪽 사용 | 6.2, 함정 3 |
| B-3 `RemoteIpFilter` | `native` 전략: 신뢰 프록시 걷어내고 오른쪽부터 | 6.2, 6.3 |

## 3. 잘못된 코드 먼저

### 3.1 프록시 뒤에서 클라이언트 IP·URL을 그대로 쓰는 코드

```java
package proxy.bad;

import jakarta.servlet.http.HttpServletRequest;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class BadAuditController {

    @GetMapping("/audit")
    public String audit(HttpServletRequest request) {
        // 문제 1: 프록시 뒤에서는 항상 프록시 IP. 모든 사용자가 같은 IP로 기록된다.
        String ip = request.getRemoteAddr();
        // 문제 2: TLS 종료 뒤에서는 http://내부IP:8080/... 이 만들어진다.
        String selfUrl = request.getRequestURL().toString();
        return ip + " " + selfUrl;
    }
}
```

### 3.2 "고친다"며 헤더를 직접 파싱하는 코드 — 더 나쁘다

```java
package proxy.bad;

import jakarta.servlet.http.HttpServletRequest;

public final class NaiveClientIp {

    private NaiveClientIp() {
    }

    public static String resolve(HttpServletRequest request) {
        String xff = request.getHeader("X-Forwarded-For");
        if (xff != null && !xff.isBlank()) {
            // 맨 왼쪽 값은 클라이언트가 직접 써 넣을 수 있다.
            // 이 값으로 IP 화이트리스트를 검사하면 헤더 하나로 우회된다.
            return xff.split(",")[0].trim();
        }
        return request.getRemoteAddr();
    }
}
```

문제 요약: 3.1은 **틀린 값**, 3.2는 **위조 가능한 값**을 쓴다. 해결은 "직접 파싱하지 말고, 신뢰 프록시를 아는 계층(웹 서버·필터)에 맡긴다"이다.

## 4. 개선된 코드 (단계적으로)

### 1단계 — 리버스 프록시가 전달 헤더를 붙이게 한다 (Nginx)

전달 헤더가 없으면 Spring이 아무리 설정해도 알 방법이 없다.

```nginx
upstream app {
    server 10.0.1.11:8080;
    server 10.0.1.12:8080;
    keepalive 32;                       # 업스트림 연결 재사용
}

server {
    listen 443 ssl;
    server_name shop.example.com;
    # ssl_certificate ... (TLS 종료)

    client_max_body_size 20m;           # 기본 1m → 함정 4

    location /api/ {
        proxy_pass http://app;
        proxy_http_version 1.1;          # 기본 1.0 → keepalive/WebSocket 불가
        proxy_set_header Connection "";  # keepalive를 위해 hop-by-hop 'close' 제거
        proxy_set_header Host              $host;
        proxy_set_header X-Forwarded-For   $remote_addr;   # 최전방이므로 '덮어쓰기' (위조값 제거)
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-Host  $host;
        proxy_set_header X-Forwarded-Port  $server_port;
        proxy_read_timeout 120s;         # 기본 60s → 함정 4
    }

    location /api/sse/ {
        proxy_pass http://app;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_buffering off;             # SSE 이벤트 즉시 전달 → 함정 5
        proxy_read_timeout 1h;
    }

    location /ws/ {
        proxy_pass http://app;
        proxy_http_version 1.1;
        proxy_set_header Upgrade    $http_upgrade;  # hop-by-hop이라 명시적으로 전달 → 함정 5
        proxy_set_header Connection "upgrade";
    }
}
```

> 앞에 다른 프록시(CDN, ALB)가 또 있다면 `X-Forwarded-For $remote_addr` 대신 `$proxy_add_x_forwarded_for`(기존 값에 덧붙임)를 쓰고, 맨 앞 프록시에서만 덮어쓴다.

**좋아진 점**: 업스트림이 원래 클라이언트 IP·스킴·호스트를 알 수 있는 **재료**가 생겼다. 최전방에서 덮어쓰므로 클라이언트가 보낸 위조 XFF가 사라진다.

### 2단계 — Spring Boot가 헤더를 해석하게 한다 (properties 설정)

```properties
# application.properties
# native: Tomcat RemoteIpValve가 처리. 연결 상대가 internal-proxies에 맞을 때만 헤더 신뢰
server.forward-headers-strategy=native
# 프록시가 기본 사설 대역 밖에 있으면 명시 (정규식)
server.tomcat.remoteip.internal-proxies=10\\.0\\.0\\.\\d{1,3}
server.tomcat.remoteip.remote-ip-header=X-Forwarded-For
server.tomcat.remoteip.protocol-header=X-Forwarded-Proto
```

**좋아진 점**: 3.1의 `BadAuditController`를 **코드 수정 없이** 올바른 값으로 바꾼다. `getRemoteAddr()`=실제 클라이언트, `getRequestURL()`=`https://shop.example.com/...`, `isSecure()`=true → Spring Security·OAuth2 리다이렉트도 함께 고쳐진다.

### 3단계 — 애플리케이션 코드는 서블릿 API만 쓴다

```java
package proxy.good;

import jakarta.servlet.http.HttpServletRequest;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;
import org.springframework.web.servlet.support.ServletUriComponentsBuilder;

@RestController
public class WhoAmIController {

    @GetMapping("/whoami")
    public String whoami(HttpServletRequest request) {
        // 전달 헤더 해석은 웹 서버/필터의 책임. 여기서는 표준 API만 호출한다.
        // 그래서 프록시 구성이 바뀌어도 이 코드는 바뀌지 않는다.
        String self = ServletUriComponentsBuilder.fromCurrentRequest().toUriString();
        return "remote=" + request.getRemoteAddr()
                + " scheme=" + request.getScheme()
                + " secure=" + request.isSecure()
                + " self=" + self;
    }
}
```

**좋아진 점**: 3.2처럼 헤더를 직접 파싱하는 코드가 사라졌다. 신뢰 판단은 한 곳(설정)에만 있다.

### 4단계 — 외부 API 호출 시 포워드 프록시 (사내망)

```java
package proxy.good;

import java.net.InetSocketAddress;
import java.net.ProxySelector;
import java.net.http.HttpClient;
import java.time.Duration;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.client.JdkClientHttpRequestFactory;
import org.springframework.web.client.RestClient;

@Configuration
public class OutboundProxyConfig {

    @Bean
    RestClient partnerRestClient() {
        HttpClient httpClient = HttpClient.newBuilder()
                // 기본값에 기대지 않고 명시. OS 환경변수 HTTPS_PROXY는 JVM이 읽지 않는다.
                .proxy(ProxySelector.of(new InetSocketAddress("proxy.corp.local", 3128)))
                .connectTimeout(Duration.ofSeconds(3))
                .build();
        return RestClient.builder()
                .requestFactory(new JdkClientHttpRequestFactory(httpClient))
                .baseUrl("https://api.partner.com")
                .build();
    }
}
```

**좋아진 점**: 외부용 클라이언트에만 프록시를 건다. 전역 `-Dhttps.proxyHost`처럼 내부 API 호출까지 프록시로 새어 나가는 일이 없다(함정 6). 전역 설정이 필요하면 `-Dhttp.nonProxyHosts="localhost|*.internal|10.*"`를 반드시 같이 둔다.

## 5. 전체 코드

### Part A — 순수 Java: 세 종류 서버를 직접 만들어 보기

설정 방식: 없음 (JDK 내장 `com.sun.net.httpserver`, `java.net.http`).

```java
package proxy;

import com.sun.net.httpserver.Headers;
import com.sun.net.httpserver.HttpExchange;
import com.sun.net.httpserver.HttpServer;
import java.io.IOException;
import java.io.OutputStream;
import java.net.InetSocketAddress;
import java.net.ProxySelector;
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.nio.charset.StandardCharsets;
import java.util.Set;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class ProxyDemo {

    static final int ORIGIN_PORT = 9000;
    static final int FORWARD_PROXY_PORT = 8888;
    static final int REVERSE_PROXY_PORT = 8080;

    // 프록시가 뒤쪽으로 요청할 때 쓰는 클라이언트.
    // NO_PROXY: 프록시 자신이 다시 프록시를 타지 않게 한다 (무한 루프 방지).
    static final HttpClient UPSTREAM_CLIENT = HttpClient.newBuilder()
            .proxy(HttpClient.Builder.NO_PROXY)
            .build();

    // 리버스 프록시가 '자기 것'이라고 아는 프록시 주소. 실무의 internal-proxies에 해당.
    static final Set<String> TRUSTED_PROXIES = Set.of("127.0.0.1");

    public static void main(String[] args) throws Exception {
        // Java 21: 요청마다 가상 스레드. 프록시 핸들러가 업스트림 응답을 기다리며 블로킹해도 부담이 없다.
        ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor();
        HttpServer origin = startOrigin(executor);
        HttpServer forward = startForwardProxy(executor);
        HttpServer reverse = startReverseProxy(executor);

        try {
            HttpClient direct = HttpClient.newBuilder()
                    .proxy(HttpClient.Builder.NO_PROXY)
                    .build();
            HttpClient viaForwardProxy = HttpClient.newBuilder()
                    // 포워드 프록시의 본질: '클라이언트'가 프록시를 설정한다.
                    .proxy(ProxySelector.of(new InetSocketAddress("127.0.0.1", FORWARD_PROXY_PORT)))
                    .build();

            System.out.println("== A-1 직접 호출 ==");
            call(direct, "http://127.0.0.1:" + ORIGIN_PORT + "/hello", null);

            System.out.println("== A-2 포워드 프록시 경유 (목적지 URL은 원본 그대로) ==");
            call(viaForwardProxy, "http://127.0.0.1:" + ORIGIN_PORT + "/hello", null);

            System.out.println("== A-3 리버스 프록시 경유 (클라이언트는 :8080만 안다) ==");
            call(direct, "http://127.0.0.1:" + REVERSE_PROXY_PORT + "/hello", null);

            System.out.println("== A-4 리버스 프록시에 위조 X-Forwarded-For 전송 ==");
            call(direct, "http://127.0.0.1:" + REVERSE_PROXY_PORT + "/hello", "9.9.9.9");
        } finally {
            reverse.stop(0);
            forward.stop(0);
            origin.stop(0);
            executor.close();
        }
    }

    // ---------- 원본 서버: 자기가 본 것을 그대로 출력 ----------
    static HttpServer startOrigin(ExecutorService executor) throws IOException {
        HttpServer server = HttpServer.create(new InetSocketAddress("127.0.0.1", ORIGIN_PORT), 0);
        server.createContext("/", exchange -> {
            Headers h = exchange.getRequestHeaders();
            String xff = h.getFirst("X-Forwarded-For");
            String report = "requestTarget=" + exchange.getRequestURI()
                    + " | tcpPeer=" + exchange.getRemoteAddress()
                    + " | Host=" + h.getFirst("Host")
                    + " | XFF=" + xff
                    + " | XFHost=" + h.getFirst("X-Forwarded-Host")
                    + " | naiveIp=" + naiveClientIp(xff, exchange)
                    + " | safeIp=" + safeClientIp(xff, exchange);
            System.out.println("  [origin] " + report);
            respond(exchange, 200, "hello from origin");
        });
        server.setExecutor(executor);
        server.start();
        return server;
    }

    // ---------- 포워드 프록시: 요청 안의 '절대 URL'로 목적지를 정한다 ----------
    static HttpServer startForwardProxy(ExecutorService executor) throws IOException {
        HttpServer server = HttpServer.create(new InetSocketAddress("127.0.0.1", FORWARD_PROXY_PORT), 0);
        server.createContext("/", exchange -> {
            URI target = exchange.getRequestURI();
            System.out.println("  [forward-proxy] request line target = " + target);
            if (!target.isAbsolute()) {
                // absolute-form이 아니면 '프록시로서' 받은 요청이 아니다.
                respond(exchange, 400, "forward proxy expects absolute-form request-target");
                return;
            }
            relay(exchange, target);
        });
        server.setExecutor(executor);
        server.start();
        return server;
    }

    // ---------- 리버스 프록시: 자기 설정(고정 업스트림)으로 목적지를 정한다 ----------
    static HttpServer startReverseProxy(ExecutorService executor) throws IOException {
        HttpServer server = HttpServer.create(new InetSocketAddress("127.0.0.1", REVERSE_PROXY_PORT), 0);
        server.createContext("/", exchange -> {
            URI incoming = exchange.getRequestURI();               // origin-form: /hello
            URI upstream = URI.create("http://127.0.0.1:" + ORIGIN_PORT + incoming);
            System.out.println("  [reverse-proxy] " + incoming + " -> " + upstream);
            relay(exchange, upstream);
        });
        server.setExecutor(executor);
        server.start();
        return server;
    }

    // ---------- 두 프록시 공통: 새 연결로 다시 요청하고 응답을 복사 ----------
    static void relay(HttpExchange exchange, URI upstream) throws IOException {
        String peerIp = exchange.getRemoteAddress().getAddress().getHostAddress();
        String priorXff = exchange.getRequestHeaders().getFirst("X-Forwarded-For");
        // 표준 관례: 기존 값 오른쪽에 '나에게 연결한 상대'를 덧붙인다.
        String xff = (priorXff == null) ? peerIp : priorXff + ", " + peerIp;

        HttpRequest.Builder builder = HttpRequest.newBuilder(upstream)
                .header("X-Forwarded-For", xff)
                .header("X-Forwarded-Proto", "http");
        String originalHost = exchange.getRequestHeaders().getFirst("Host");
        if (originalHost != null) {
            // Host는 JDK HttpClient의 제한 헤더라 바꿀 수 없다 (업스트림 주소로 자동 설정).
            // 그래서 원래 Host는 X-Forwarded-Host로 따로 전달한다.
            builder.header("X-Forwarded-Host", originalHost);
        }

        try {
            HttpResponse<byte[]> upstreamResponse =
                    UPSTREAM_CLIENT.send(builder.GET().build(), HttpResponse.BodyHandlers.ofByteArray());
            respond(exchange, upstreamResponse.statusCode(), upstreamResponse.body());
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            respond(exchange, 502, "interrupted");
        } catch (IOException e) {
            // 업스트림 연결 실패 → 프록시가 만들어 내는 502. 원본 서버는 이 요청을 보지 못한다.
            respond(exchange, 502, "bad gateway: " + e.getMessage());
        }
    }

    // ---------- 클라이언트 IP 판단 두 가지 ----------
    static String naiveClientIp(String xff, HttpExchange exchange) {
        if (xff == null) {
            return exchange.getRemoteAddress().getAddress().getHostAddress();
        }
        return xff.split(",")[0].trim();   // 맨 왼쪽: 위조 가능
    }

    static String safeClientIp(String xff, HttpExchange exchange) {
        String peer = exchange.getRemoteAddress().getAddress().getHostAddress();
        if (!TRUSTED_PROXIES.contains(peer) || xff == null) {
            // 신뢰하지 않는 상대가 보낸 XFF는 아예 보지 않는다.
            return peer;
        }
        String[] hops = xff.split(",");
        for (int i = hops.length - 1; i >= 0; i--) {
            String hop = hops[i].trim();
            if (!TRUSTED_PROXIES.contains(hop)) {
                return hop;   // 오른쪽부터 신뢰 프록시를 걷어낸 첫 값
            }
        }
        return hops[0].trim();
    }

    // ---------- 유틸 ----------
    static void call(HttpClient client, String url, String spoofedXff) throws Exception {
        HttpRequest.Builder b = HttpRequest.newBuilder(URI.create(url)).GET();
        if (spoofedXff != null) {
            b.header("X-Forwarded-For", spoofedXff);
        }
        HttpResponse<String> res = client.send(b.build(), HttpResponse.BodyHandlers.ofString());
        System.out.println("  [client] " + res.statusCode() + " " + res.body());
    }

    static void respond(HttpExchange exchange, int status, String body) throws IOException {
        respond(exchange, status, body.getBytes(StandardCharsets.UTF_8));
    }

    static void respond(HttpExchange exchange, int status, byte[] body) throws IOException {
        exchange.sendResponseHeaders(status, body.length);
        try (OutputStream os = exchange.getResponseBody()) {
            os.write(body);
        }
    }
}
```

> 데모 단순화를 위해 GET만, 응답 헤더는 복사하지 않는다. 실제 프록시는 메서드·본문·응답 헤더를 전달하고 hop-by-hop 헤더(`Connection`, `Transfer-Encoding` 등)는 제거한다.
> 신뢰 프록시가 모두 127.0.0.1이라 A-4에서 safeIp도 '127.0.0.1'을 걷어낸 뒤의 값을 고른다. 실제 환경에서는 클라이언트·프록시 IP가 서로 달라 구분이 더 명확하다.

**하위 버전 대응**

- **Java 11~20**: `Executors.newVirtualThreadPerTaskExecutor()` → `Executors.newFixedThreadPool(16)`, `executor.close()` → `executor.shutdown()`. 나머지는 그대로 동작한다.
- **Java 8** (`java.net.http` 없음): 클라이언트 쪽 프록시 지정은 `HttpURLConnection`으로 한다.

```java
package proxy.java8;

import java.io.BufferedReader;
import java.io.InputStreamReader;
import java.net.HttpURLConnection;
import java.net.InetSocketAddress;
import java.net.Proxy;
import java.net.URL;

public class Java8ForwardProxyClient {

    public static void main(String[] args) throws Exception {
        Proxy proxy = new Proxy(Proxy.Type.HTTP, new InetSocketAddress("127.0.0.1", 8888));
        URL url = new URL("http://127.0.0.1:9000/hello");
        // openConnection(Proxy)는 ProxySelector·시스템 프로퍼티를 무시하고 이 프록시만 쓴다.
        HttpURLConnection conn = (HttpURLConnection) url.openConnection(proxy);
        try (BufferedReader in = new BufferedReader(
                new InputStreamReader(conn.getInputStream(), "UTF-8"))) {
            System.out.println(conn.getResponseCode() + " " + in.readLine());
        } finally {
            conn.disconnect();
        }
    }
}
```

> 주의: `HttpURLConnection`은 기본 `ProxySelector`를 거칠 때 `http.nonProxyHosts` 기본값(localhost, 127.*)을 우회 대상으로 본다. 위처럼 `openConnection(Proxy)`로 명시하면 그 규칙을 타지 않는다 (확인 필요: JDK 벤더별 차이).

## 6. 실행 결과

> 이 문서 작성 환경에서는 실행하지 못했다. 아래는 모두 **예상 출력**이다. 임시 포트 번호(`5xxxx`)는 실행마다 달라진다.

### Part A

```text
== A-1 직접 호출 ==
  [origin] requestTarget=/hello | tcpPeer=/127.0.0.1:53011 | Host=127.0.0.1:9000 | XFF=null | XFHost=null | naiveIp=127.0.0.1 | safeIp=127.0.0.1
  [client] 200 hello from origin
== A-2 포워드 프록시 경유 (목적지 URL은 원본 그대로) ==
  [forward-proxy] request line target = http://127.0.0.1:9000/hello
  [origin] requestTarget=/hello | tcpPeer=/127.0.0.1:53020 | Host=127.0.0.1:9000 | XFF=127.0.0.1 | XFHost=127.0.0.1:9000 | naiveIp=127.0.0.1 | safeIp=127.0.0.1
  [client] 200 hello from origin
== A-3 리버스 프록시 경유 (클라이언트는 :8080만 안다) ==
  [reverse-proxy] /hello -> http://127.0.0.1:9000/hello
  [origin] requestTarget=/hello | tcpPeer=/127.0.0.1:53025 | Host=127.0.0.1:9000 | XFF=127.0.0.1 | XFHost=127.0.0.1:8080 | naiveIp=127.0.0.1 | safeIp=127.0.0.1
  [client] 200 hello from origin
== A-4 리버스 프록시에 위조 X-Forwarded-For 전송 ==
  [reverse-proxy] /hello -> http://127.0.0.1:9000/hello
  [origin] requestTarget=/hello | tcpPeer=/127.0.0.1:53031 | Host=127.0.0.1:9000 | XFF=9.9.9.9, 127.0.0.1 | XFHost=127.0.0.1:8080 | naiveIp=9.9.9.9 | safeIp=9.9.9.9
  [client] 200 hello from origin
```

읽는 법:

- **A-2의 `[forward-proxy] request line target`이 `http://...` 전체 URL**이다(absolute-form). A-3의 리버스 프록시는 `/hello`만 받는다. 목적지를 "요청이 알려주느냐(포워드)" vs "프록시 설정이 정하느냐(리버스)"의 차이가 여기서 보인다.
- A-2·A-3 모두 `tcpPeer`의 포트가 클라이언트가 아니라 **프록시가 새로 연 연결**의 포트다.
- A-3의 `XFHost=127.0.0.1:8080`: 클라이언트가 실제로 호출한 주소. 원본 서버가 자기 URL을 만들 때 써야 할 값이다.
- **A-4**: 데모에서는 클라이언트·프록시가 모두 127.0.0.1이어서 `safeIp`도 신뢰 프록시(127.0.0.1)를 걷어낸 뒤 9.9.9.9에 도달한다. 실제 환경(클라이언트 1.1.1.1, 프록시 10.0.0.5)이라면 XFF는 `9.9.9.9, 1.1.1.1`이 되고 naive=9.9.9.9(위조), safe=1.1.1.1(진짜)로 갈린다. 이 차이는 Part B 테스트에서 정확히 검증한다.

### Part B — curl 결과 (strategy별)

```text
# server.forward-headers-strategy=none
remote=127.0.0.1 scheme=http secure=false self=http://127.0.0.1:8080/whoami

# server.forward-headers-strategy=native  (127.0.0.1은 기본 internal-proxies에 포함 → 헤더 신뢰)
remote=203.0.113.7 scheme=https secure=true self=https://shop.example.com/whoami

# server.forward-headers-strategy=framework
remote=203.0.113.7 scheme=https secure=true self=https://shop.example.com/whoami
```

> `native`에서 4장 2단계처럼 `internal-proxies`를 `10.0.0.x`로 좁혀 두었다면, 127.0.0.1에서 보낸 curl의 헤더는 **무시**되어 `none`과 같은 결과가 나온다. 이것이 native 전략의 보호 장치다. `self`의 포트 표기(`:443` 생략 여부)는 `X-Forwarded-Port` 유무에 따라 달라질 수 있다.

## 7. 검증 코드 (JUnit 5)

Spring Boot 컨텍스트 없이 `MockMvc` standalone으로 필터만 바꿔 끼운다. 그래야 "어느 필터가 무엇을 바꾸는가"만 정확히 보인다.

- `MockHttpServletRequest`의 기본 `remoteAddr`는 `127.0.0.1` → 리버스 프록시가 127.0.0.1에서 연결했다고 가정한 상황.
- `ForwardedHeaderFilter` = `framework` 전략, `RemoteIpFilter` = `native` 전략(`RemoteIpValve`)과 같은 로직의 Tomcat 서블릿 필터.

```java
package proxy.good;

import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.content;

import org.apache.catalina.filters.RemoteIpFilter;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;
import org.springframework.test.web.servlet.MockMvc;
import org.springframework.test.web.servlet.setup.MockMvcBuilders;
import org.springframework.web.filter.ForwardedHeaderFilter;

class ForwardedHeadersTest {

    @Test
    @DisplayName("B-1: 헤더 해석이 없으면 remoteAddr는 프록시, scheme은 http")
    void noStrategy() throws Exception {
        MockMvc mvc = MockMvcBuilders.standaloneSetup(new WhoAmIController()).build();

        mvc.perform(get("/whoami")
                        .header("X-Forwarded-For", "203.0.113.7")
                        .header("X-Forwarded-Proto", "https")
                        .header("X-Forwarded-Host", "shop.example.com"))
                .andExpect(content().string(
                        "remote=127.0.0.1 scheme=http secure=false self=http://localhost/whoami"));
    }

    @Test
    @DisplayName("B-2: ForwardedHeaderFilter는 스킴·호스트·remoteAddr을 헤더 값으로 바꾼다")
    void frameworkStrategy() throws Exception {
        MockMvc mvc = MockMvcBuilders.standaloneSetup(new WhoAmIController())
                .addFilters(new ForwardedHeaderFilter())
                .build();

        mvc.perform(get("/whoami")
                        .header("X-Forwarded-For", "203.0.113.7")
                        .header("X-Forwarded-Proto", "https")
                        .header("X-Forwarded-Host", "shop.example.com"))
                .andExpect(content().string(
                        "remote=203.0.113.7 scheme=https secure=true self=https://shop.example.com/whoami"));
    }

    @Test
    @DisplayName("B-2': ForwardedHeaderFilter는 XFF 맨 왼쪽(위조 가능 값)을 remoteAddr로 쓴다")
    void frameworkStrategyTrustsLeftmost() throws Exception {
        MockMvc mvc = MockMvcBuilders.standaloneSetup(new WhoAmIController())
                .addFilters(new ForwardedHeaderFilter())
                .build();

        // 클라이언트(1.1.1.1)가 9.9.9.9를 위조해 보냈고, 프록시가 1.1.1.1을 덧붙인 상황
        mvc.perform(get("/whoami").header("X-Forwarded-For", "9.9.9.9, 1.1.1.1"))
                .andExpect(content().string(org.hamcrest.Matchers.startsWith("remote=9.9.9.9 ")));
    }

    @Test
    @DisplayName("B-3: RemoteIpFilter는 오른쪽부터 신뢰 프록시를 걷어낸 첫 값을 쓴다")
    void nativeStrategyTakesRightmostUntrusted() throws Exception {
        RemoteIpFilter remoteIpFilter = new RemoteIpFilter();
        // 연결 상대(127.0.0.1)가 내부 프록시로 인정되어야 헤더를 본다.
        remoteIpFilter.setInternalProxies("127\\.0\\.0\\.1");
        remoteIpFilter.setRemoteIpHeader("X-Forwarded-For");
        remoteIpFilter.setProtocolHeader("X-Forwarded-Proto");

        MockMvc mvc = MockMvcBuilders.standaloneSetup(new WhoAmIController())
                .addFilters(remoteIpFilter)
                .build();

        mvc.perform(get("/whoami")
                        .header("X-Forwarded-For", "9.9.9.9, 1.1.1.1")
                        .header("X-Forwarded-Proto", "https"))
                .andExpect(content().string(org.hamcrest.Matchers.startsWith(
                        "remote=1.1.1.1 scheme=https secure=true")));
    }

    @Test
    @DisplayName("B-3': 연결 상대가 신뢰 프록시가 아니면 RemoteIpFilter는 헤더를 무시한다")
    void nativeStrategyIgnoresUntrustedPeer() throws Exception {
        RemoteIpFilter remoteIpFilter = new RemoteIpFilter();
        remoteIpFilter.setInternalProxies("10\\.0\\.0\\.\\d{1,3}");   // 127.0.0.1은 신뢰 범위 밖
        remoteIpFilter.setRemoteIpHeader("X-Forwarded-For");
        remoteIpFilter.setProtocolHeader("X-Forwarded-Proto");

        MockMvc mvc = MockMvcBuilders.standaloneSetup(new WhoAmIController())
                .addFilters(remoteIpFilter)
                .build();

        // 프록시를 거치지 않고 앱 포트로 직접 위조 헤더를 보낸 공격 상황
        mvc.perform(get("/whoami")
                        .header("X-Forwarded-For", "10.0.0.1")
                        .header("X-Forwarded-Proto", "https"))
                .andExpect(content().string(org.hamcrest.Matchers.startsWith(
                        "remote=127.0.0.1 scheme=http secure=false")));
    }
}
```

예상 결과: 5개 모두 통과. 확인 필요 지점:

- `MockHttpServletRequest` 기본 서버명이 `localhost`, 포트 80이라 B-1의 `self`는 `http://localhost/whoami`로 예상한다.
- `RemoteIpFilter` 세터 이름(`setInternalProxies`, `setRemoteIpHeader`, `setProtocolHeader`)은 Tomcat 10.1 기준. 버전에 따라 `init-param`으로만 설정되는 항목이 있으면 `MockFilterConfig`로 `init()`을 호출해 설정한다.
- `RemoteIpFilter`는 `X-Forwarded-Proto: https`일 때 서버 포트를 443으로 바꾸는 등 추가 동작이 있어 `self` 값은 단언하지 않았다.

## 8. 변형 실습

1. **Part A에서 `UPSTREAM_CLIENT`의 `NO_PROXY`를 지우고 JVM을 `-Dhttp.proxyHost=127.0.0.1 -Dhttp.proxyPort=8888`로 실행하면?**
   포워드 프록시가 원본으로 보내는 요청이 다시 자기 자신(포워드 프록시)으로 들어올 수 있다. 실제 결과는 `HttpClient` 기본 셀렉터의 동작과 `nonProxyHosts` 기본값(127.*)에 따라 갈린다 — 둘 중 무엇이 일어나는지 직접 확인하고, 왜 프록시 자신은 명시적으로 `NO_PROXY`를 써야 하는지 정리해 보라.

2. **Part A 원본 서버 핸들러에 `Thread.sleep(5000)`을 넣고, `UPSTREAM_CLIENT` 요청에 `.timeout(Duration.ofSeconds(2))`를 걸면?**
   클라이언트는 502(프록시가 만든 응답)를 받지만 원본 서버 로그는 5초 뒤 정상 처리 완료를 찍는다. 이론 문서 함정 4의 "프록시는 끊었는데 서버는 계속 일한다 → 재시도 시 중복 처리"를 눈으로 확인하는 실습이다.

3. **Part B에서 `forward-headers-strategy=framework`로 두고, Nginx를 거치지 않고 앱 포트로 직접 `X-Forwarded-For: 10.0.0.1`을 보내면?**
   `getRemoteAddr()`가 `10.0.0.1`이 된다. 이 값으로 "사내 IP만 허용" 검사를 하는 인터셉터를 만들어 우회되는 것을 확인하고, `native` + 좁힌 `internal-proxies`로 바꿨을 때 막히는지(B-3' 테스트와 같은 결과) 비교해 보라.
