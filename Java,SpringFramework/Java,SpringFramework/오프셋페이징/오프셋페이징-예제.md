# 오프셋 페이징 예제 — 중복·누락·count·깊은 페이지를 눈으로 확인하기

관련 문서: [이론](./오프셋페이징-이론.md)

---

## 1. 예제 개요

게시글(`post`) 목록 API를 오프셋 페이징으로 만든다. 처음에는 흔히 쓰는 잘못된 형태로 만들고, 단계별로 고친다.
테스트는 Testcontainers PostgreSQL에서 실제 SQL로 검증한다.

테스트 데이터는 **10건마다 `created_at`이 같은** 1,000건이다. 정렬 키 동점(tie) 상황을 일부러 만든 것이다.

| 검증하는 개념 | 이론 문서 | 이 문서 |
|---|---|---|
| DB 페이징 vs 메모리 페이징 | 2장, 7장 | 3.1, 4 단계 1 |
| 결정적 정렬 (tie-breaker) | 6장, 8.1 | 3.2, 4 단계 2, 테스트 ① |
| 페이지 사이 INSERT로 인한 중복, 기준 시각 고정 | 5.3, 8.4 | 테스트 ②③ |
| `Page`의 count 쿼리, `Slice`의 size+1, count 생략 조건 | 6장, 8.3 | 4 단계 4, 테스트 ④⑤ |
| 깊은 페이지와 지연 조인 | 5.2, 8.2 | 4 단계 5, 6.3, 테스트 ⑥ |
| page/size/sort 입력 검증 | 8.6 | 3.2, 4 단계 3, 테스트 ⑦ |

## 3. 잘못된 코드 먼저

### 3.1 메모리 페이징

```java
// 잘못된 예: 전부 조회한 뒤 JVM에서 자른다
public List<Post> getPage(int page, int size) {
    List<Post> all = postRepository.findAll(Sort.by(Sort.Direction.DESC, "createdAt"));
    int from = Math.min(page * size, all.size());
    int to = Math.min(from + size, all.size());
    return all.subList(from, to);
}
```

실행되는 SQL:

```sql
select p1_0.id, p1_0.created_at, p1_0.title from post p1_0 order by p1_0.created_at desc
-- LIMIT도 OFFSET도 없다
```

문제점:
- 테이블 전체를 읽어 전송하고, **모든 행을 엔티티로 만들어 영속성 컨텍스트에 등록**한다. 메모리 사용량이 테이블 크기에 비례한다.
- `subList`는 원본 리스트의 뷰(view)라서 반환한 뒤에도 전체 리스트가 GC되지 않는다.

### 3.2 DB 페이징은 했지만 함정을 그대로 둔 코드

```java
@RestController
@RequestMapping("/bad/posts")
public class BadPostController {

    private final PostRepository postRepository;

    public BadPostController(PostRepository postRepository) {
        this.postRepository = postRepository;
    }

    @GetMapping
    public Page<Post> list(@PageableDefault(size = 20, sort = "createdAt",
                                            direction = Sort.Direction.DESC) Pageable pageable) {
        return postRepository.findAll(pageable);
    }
}
```

문제점 (이론 8장 번호):

| 문제 | 이론 | 결과 |
|---|---|---|
| `createdAt` 하나로만 정렬 | 8.1 | 동점 행이 페이지 사이에서 겹치거나 빠진다 |
| `Pageable`을 그대로 받음 | 8.6 | page는 0부터, size는 최대 2000, `sort=title` 같은 임의 정렬 허용 |
| 항상 `Page` 반환 | 8.3 | 화면이 총 개수를 안 써도 매 요청마다 count 쿼리 |
| 엔티티 `Page`를 그대로 JSON 반환 | 10장 | 엔티티 구조가 API로 노출되고, Spring Data 3.3+에서 `PageImpl` 직렬화 경고 |
| 깊은 페이지 제한 없음 | 8.2 | `?page=50000` 한 번이 offset 1,000,000 스캔 |

## 4. 개선된 코드

### 단계 1 — 페이징을 DB로 내린다

```java
Page<Post> page = postRepository.findAll(PageRequest.of(pageIndex, size, sort));
```

- 좋아진 점: SQL에 `offset ? rows fetch first ? rows only`가 붙어 **size건만** 전송·생성된다.

### 단계 2 — 정렬을 결정적으로 만든다

```java
Sort latest = Sort.by(Sort.Order.desc("createdAt"), Sort.Order.desc("id"));
```

```sql
create index idx_post_created_at_id on post (created_at desc, id desc);
```

- 좋아진 점: `(created_at, id)` 조합은 유일하므로 **모든 행의 순번이 하나로 정해진다.** 같은 인덱스가 정렬 순서와 일치해 실행 계획에서 `Sort` 노드도 사라진다.

### 단계 3 — 입력을 서버가 통제한다

```java
public enum PostSort {
    LATEST(Sort.by(Sort.Order.desc("createdAt"), Sort.Order.desc("id"))),
    OLDEST(Sort.by(Sort.Order.asc("createdAt"), Sort.Order.asc("id")));
    // ...
}
```

- 좋아진 점: page는 **1부터** 받아 내부에서 0 기반으로 바꾼다. size는 최대 100으로 자른다. 정렬은 허용된 두 가지뿐이고 둘 다 인덱스를 탄다 (`OLDEST`는 같은 인덱스를 역방향으로 스캔). 1,000페이지를 넘는 요청은 400으로 거절한다.

### 단계 4 — 총 개수가 필요 없는 화면은 `Slice`

```java
Slice<Post> findSliceBy(Pageable pageable);
```

- 좋아진 점: count 쿼리가 사라진다. Spring Data가 `size + 1`건을 조회해 `hasNext()`를 판단한다.

### 단계 5 — 깊은 페이지는 지연 조인

```sql
select p.*
from post p
join (select id
      from post
      order by created_at desc, id desc
      limit :pageSize offset :skip) t on t.id = p.id
order by p.created_at desc, p.id desc
```

- 좋아진 점: 버리는 행은 서브쿼리에서 **인덱스만** 읽는다 (Index Only Scan). 본 테이블(힙)은 최종 20건에 대해서만 읽는다.
- 한계: 여전히 offset개의 인덱스 항목은 읽는다. O(offset)은 그대로이고 상수만 줄어든다. 그래서 단계 3의 최대 페이지 제한과 함께 쓴다.

`src/main/resources/schema.sql`

```sql
drop table if exists post;

create table post (
    id         bigserial    primary key,
    title      varchar(200) not null,
    created_at timestamp    not null
);

-- 정렬 순서 (created_at desc, id desc)와 똑같이 만든다.
-- 정렬 키 + tie-breaker를 모두 담아야 ① Sort 노드가 사라지고 ② 지연 조인 서브쿼리가 Index Only Scan이 된다
create index idx_post_created_at_id on post (created_at desc, id desc);
```

> **Oracle 차이**: `bigserial` 대신 `NUMBER GENERATED BY DEFAULT AS IDENTITY`(12c+), `timestamp`는 동일. 페이징 SQL은 12c+에서 `OFFSET :skip ROWS FETCH NEXT :pageSize ROWS ONLY`, 11g 이하는 `ROWNUM` 서브쿼리가 필요하다.

`post/PostRepository.java`

```java
package com.example.paging.post;

import org.springframework.data.domain.Page;
import org.springframework.data.domain.Pageable;
import org.springframework.data.domain.Slice;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;

import java.time.LocalDateTime;
import java.util.List;

public interface PostRepository extends JpaRepository<Post, Long> {

    // 반환 타입이 Slice이므로 Spring Data가 size+1건을 조회하고 count 쿼리는 만들지 않는다
    Slice<Post> findSliceBy(Pageable pageable);

    // 첫 조회 시각을 기준으로 고정해, 이후 INSERT가 순번을 밀지 못하게 한다 (이론 8.4)
    Page<Post> findByCreatedAtLessThanEqual(LocalDateTime baseTime, Pageable pageable);

    // 지연 조인: 버리는 행은 서브쿼리에서 인덱스만 읽고, 본 테이블은 최종 pageSize건만 읽는다 (이론 8.2)
    @Query(value = """
            select p.*
            from post p
            join (select id
                  from post
                  order by created_at desc, id desc
                  limit :pageSize offset :skip) t on t.id = p.id
            order by p.created_at desc, p.id desc
            """, nativeQuery = true)
    List<Post> findLatestByDeferredJoin(@Param("pageSize") int pageSize, @Param("skip") long skip);
}
```

`post/PostQueryService.java`

```java
package com.example.paging.post;

import com.example.paging.common.PageResponse;
import com.example.paging.common.SliceResponse;
import org.springframework.data.domain.Page;
import org.springframework.data.domain.PageImpl;
import org.springframework.data.domain.PageRequest;
import org.springframework.data.domain.Slice;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.util.List;

@Service
@Transactional(readOnly = true)
public class PostQueryService {

    static final int MAX_SIZE = 100;
    static final int MAX_PAGE = 1_000;
    // 이 offset부터는 일반 OFFSET 대신 지연 조인을 쓴다. 실제 값은 EXPLAIN ANALYZE로 측정해서 정한다
    static final long DEFERRED_JOIN_THRESHOLD = 10_000;

    private final PostRepository postRepository;

    public PostQueryService(PostRepository postRepository) {
        this.postRepository = postRepository;
    }

    public PageResponse<PostDto> getPage(int page, int size, PostSort sort) {
        PageRequest pageRequest = toPageRequest(page, size, sort);
        Page<Post> result = shouldUseDeferredJoin(pageRequest, sort)
                ? findByDeferredJoin(pageRequest)
                : postRepository.findAll(pageRequest);
        return PageResponse.of(result, PostDto::from);
    }

    public SliceResponse<PostDto> getSlice(int page, int size, PostSort sort) {
        Slice<Post> result = postRepository.findSliceBy(toPageRequest(page, size, sort));
        return SliceResponse.of(result, PostDto::from);
    }

    /**
     * API는 1부터 받고 Spring Data는 0부터 쓰므로 변환은 이 한곳에서만 한다.
     * 클라이언트 입력을 그대로 Pageable로 쓰지 않는 이유는 이론 8.6 참고.
     */
    PageRequest toPageRequest(int page, int size, PostSort sort) {
        if (page < 1 || page > MAX_PAGE) {
            throw new IllegalArgumentException("page는 1~" + MAX_PAGE + " 사이여야 합니다: " + page);
        }
        int safeSize = Math.max(1, Math.min(size, MAX_SIZE));
        return PageRequest.of(page - 1, safeSize, sort.toSort());
    }

    private boolean shouldUseDeferredJoin(PageRequest pageRequest, PostSort sort) {
        // 지연 조인 쿼리는 LATEST 순서로만 작성돼 있다
        return sort == PostSort.LATEST && pageRequest.getOffset() >= DEFERRED_JOIN_THRESHOLD;
    }

    private Page<Post> findByDeferredJoin(PageRequest pageRequest) {
        List<Post> content = postRepository.findLatestByDeferredJoin(
                pageRequest.getPageSize(), pageRequest.getOffset());
        return new PageImpl<>(content, pageRequest, postRepository.count());
    }
}
```

`post/PostController.java`

```java
package com.example.paging.post;

import com.example.paging.common.PageResponse;
import com.example.paging.common.SliceResponse;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

import java.util.Map;

@RestController
@RequestMapping("/posts")
public class PostController {

    private final PostQueryService postQueryService;

    public PostController(PostQueryService postQueryService) {
        this.postQueryService = postQueryService;
    }

    // 페이지 번호 UI용: 총 개수가 필요하므로 Page
    @GetMapping
    public PageResponse<PostDto> list(@RequestParam(defaultValue = "1") int page,
                                      @RequestParam(defaultValue = "20") int size,
                                      @RequestParam(defaultValue = "LATEST") PostSort sort) {
        return postQueryService.getPage(page, size, sort);
    }

    // "더 보기" 버튼용: 다음 페이지 유무만 필요하므로 Slice
    @GetMapping("/more")
    public SliceResponse<PostDto> more(@RequestParam(defaultValue = "1") int page,
                                       @RequestParam(defaultValue = "20") int size,
                                       @RequestParam(defaultValue = "LATEST") PostSort sort) {
        return postQueryService.getSlice(page, size, sort);
    }

    @ExceptionHandler(IllegalArgumentException.class)
    public ResponseEntity<Map<String, String>> badRequest(IllegalArgumentException e) {
        return ResponseEntity.badRequest().body(Map.of("message", e.getMessage()));
    }
}
```

`common/PageResponse.java`

```java
package com.example.paging.common;

import org.springframework.data.domain.Page;

import java.util.List;
import java.util.function.Function;

/**
 * PageImpl을 그대로 직렬화하지 않고 API 계약을 고정하기 위한 응답 타입.
 * page는 API 규칙에 맞춰 1부터 내보낸다.
 */
public record PageResponse<T>(List<T> content, int page, int size,
                              long totalElements, int totalPages, boolean hasNext) {

    public static <E, T> PageResponse<T> of(Page<E> page, Function<E, T> mapper) {
        return new PageResponse<>(
                page.getContent().stream().map(mapper).toList(),
                page.getNumber() + 1,
                page.getSize(),
                page.getTotalElements(),
                page.getTotalPages(),
                page.hasNext());
    }
}
```

### 5.3 Java 8 대응 코드

Spring Boot 3.x는 Java 17 이상이 필요하다. Java 8 코드베이스(Spring Boot 2.x, `javax.persistence`)에서는 다음처럼 바꾼다. 페이징 동작 자체는 같다.

| Java 21 코드 | Java 8 대응 |
|---|---|
| `jakarta.persistence.*` | `javax.persistence.*` |
| `record PostDto(...)` | 아래 클래스 |
| 텍스트 블록 `"""` | 문자열 연결 |
| `stream().toList()` | `collect(Collectors.toList())` |
| `Map.of(...)` | `Collections.singletonMap(...)` |

```java
package com.example.paging.common;

import org.springframework.data.domain.Page;

import java.util.Collections;
import java.util.List;
import java.util.function.Function;
import java.util.stream.Collectors;

public final class PageResponse<T> {

    private final List<T> content;
    private final int page;
    private final int size;
    private final long totalElements;
    private final int totalPages;
    private final boolean hasNext;

    private PageResponse(List<T> content, int page, int size,
                         long totalElements, int totalPages, boolean hasNext) {
        this.content = Collections.unmodifiableList(content);
        this.page = page;
        this.size = size;
        this.totalElements = totalElements;
        this.totalPages = totalPages;
        this.hasNext = hasNext;
    }

    public static <E, T> PageResponse<T> of(Page<E> page, Function<E, T> mapper) {
        return new PageResponse<T>(
                page.getContent().stream().map(mapper).collect(Collectors.toList()),
                page.getNumber() + 1,
                page.getSize(),
                page.getTotalElements(),
                page.getTotalPages(),
                page.hasNext());
    }

    // Jackson이 getter로 프로퍼티를 찾으므로 getter가 필요하다
    public List<T> getContent() { return content; }
    public int getPage() { return page; }
    public int getSize() { return size; }
    public long getTotalElements() { return totalElements; }
    public int getTotalPages() { return totalPages; }
    public boolean isHasNext() { return hasNext; }
}
```

```text
Sort  (actual time=95.2..95.2 rows=20 loops=1)
  ->  Nested Loop  (actual time=95.0..95.1 rows=20 loops=1)
        ->  Limit  (actual time=94.9..94.9 rows=20 loops=1)
              ->  Index Only Scan using idx_post_created_at_id on post  (actual time=0.02..75.4 rows=900020 loops=1)
```

- 둘 다 `rows=900020`을 읽는다. **O(offset)은 그대로**다.
- 차이는 `Heap Fetches: 0`이다. 지연 조인은 버리는 행에 대해 힙을 읽지 않는다. 행이 넓을수록(긴 본문 컬럼 등) 차이가 커진다.
- `vacuum analyze` 전에 실행하면 `Heap Fetches`가 크게 나오고 이득이 줄어든다.

## 8. 변형 실습

### 실습 1 — tie-breaker를 빼면?

`PostSort.LATEST`를 `Sort.by(Sort.Order.desc("createdAt"))`로 바꾸고 인덱스를 `(created_at desc)`만으로 다시 만든다. 그다음 psql에서 동점 그룹 경계를 가로지르는 두 페이지를 서로 다른 실행 계획으로 조회해 본다.

```sql
set enable_indexscan = off;   -- 강제로 Seq Scan + Sort
select id from post order by created_at desc limit 7 offset 7;
reset enable_indexscan;
select id from post order by created_at desc limit 7 offset 7;
```

- 예상: 두 결과의 id 구성이나 순서가 다를 **수 있다**. 같은 `created_at` 안의 순서를 정해 주는 것이 없기 때문이다 (이론 6장, 8.1).
- 생각해 볼 것: 테스트 ①이 tie-breaker 없이도 통과한다면, 그것은 "안전"하다는 뜻인가?

### 실습 2 — offset 크기와 인덱스 유무에 따른 비용

6.3의 100만 건 데이터로 `offset`을 `0 / 1,000 / 100,000 / 900,000`으로 바꿔 `explain (analyze, buffers)`를 비교한다. 그다음 `drop index idx_post_created_at_id;` 후 같은 측정을 반복한다.

- 예상: 인덱스가 있으면 실행 시간이 offset에 비례해 늘어난다. 인덱스가 없으면 offset과 관계없이 매번 `Seq Scan → Sort`가 나타난다. offset이 작을 때는 `Sort Method: top-N heapsort`, 클 때는 `quicksort` 또는 `external merge`로 바뀐다.
- 생각해 볼 것: `DEFERRED_JOIN_THRESHOLD`를 어떤 근거로 정해야 하는가?

### 실습 3 — 컬렉션 fetch join과 페이징

`Comment` 엔티티를 만들고 `Post`에 `@OneToMany(mappedBy = "post") List<Comment> comments`를 추가한다. 리포지토리에 아래 메서드를 넣고 `PageRequest.of(0, 20)`으로 호출한다.

```java
@Query(value = "select distinct p from Post p left join fetch p.comments",
       countQuery = "select count(p) from Post p")
Page<Post> findWithComments(Pageable pageable);
```

- 예상: SQL에 `offset/fetch first`가 없고 `HHH90003004: firstResult/maxResults specified with collection fetch; applying in memory` 경고가 출력된다 (이론 8.5).
- 이어서 `spring.jpa.properties.hibernate.query.fail_on_pagination_over_collection_fetch=true`를 설정하면 경고 대신 예외가 나는지 확인한다.
- 해결: fetch join을 빼고 `spring.jpa.properties.hibernate.default_batch_fetch_size=100`을 설정한 뒤, 페이지 조회 SQL 1번 + 댓글 `IN` 조회 SQL 1번으로 바뀌는지 로그로 확인한다.
