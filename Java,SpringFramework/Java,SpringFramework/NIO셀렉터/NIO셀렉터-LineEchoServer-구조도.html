LineEchoServer 구조도

스레드 하나(이벤트 루프)가 모든 연결의 I/O를 맡고, 느릴 수 있는 handler는 워커 풀에서 실행하는 줄(\n) 단위 TCP 서버입니다. 그림의 색은 그 일을 어느 스레드가 실행하는지를 나타냅니다.

event-loop 스레드 워커 스레드 커널 · 채널 · Selector 호출자 스레드 (생성자, close)

전체 구조

클라이언트 연결은 모두 Selector 하나에 등록됩니다. event-loop는 준비된 채널만 골라 처리하고, 완성된 줄은 워커에게 넘깁니다. 워커는 결과를 연결에 직접 쓰지 않고 tasks 큐에 넣은 뒤 wakeup()으로 루프를 깨웁니다.

  • 생성자 L317–329
    Selector와 서버 소켓을 열고, 논블로킹으로 바꾼 뒤 OP_ACCEPT로 등록합니다. 마지막에 event-loop 스레드를 시작합니다.
  • Connection L308–315
    연결마다 하나씩 키의 attachment로 붙습니다. 읽다 만 줄(in), 못 다 보낸 응답(out), 순서용 체인(chain)을 담습니다.
  • 워커 → 루프 경로 L428–433
    워커는 연결 상태를 직접 만지지 않습니다. tasks에 작업을 넣고 깨우기만 하므로 Connection에 락이 필요 없습니다.

이벤트 루프 한 바퀴

loop() 메서드(L335–374)가 select()에서 깨어날 때마다 아래 순서로 한 바퀴를 돕니다.

  1. selector.select()L338

    준비된 채널이 생기거나, 다른 스레드가 wakeup()을 부를 때까지 잠듭니다. wakeup()이 먼저 불렸다면 다음 select()가 바로 반환되므로 깨우기 신호를 놓치지 않습니다.

  2. selectCount.incrementAndGet()L339

    깨어난 횟수를 셉니다. 유휴 상태에서 이 값이 늘면 스핀하고 있다는 뜻입니다.

  3. runTasks()L340 · L376–381

    워커가 tasks에 넣은 enqueue를 큐가 빌 때까지 실행합니다. wakeup()으로 깨어났다면 준비된 키가 하나도 없을 수 있어서 키 처리보다 먼저 합니다.

  4. selectedKeys().iterator() → it.remove()L341–345

    이번에 준비된 키만 순회하고, 꺼내자마자 집합에서 지웁니다. Selector는 이 집합을 비워 주지 않습니다.

    이 줄이 없는 BadEchoServer는 처리한 accept 키가 남아 accept()가 null을 돌려주고, select 2회 만에 NPE로 죽었습니다.

  5. if (!key.isValid()) continue;L347

    같은 순회 안에서 이미 닫힌 키는 건너뜁니다. 아래 분기들 앞에서도 isValid()를 다시 확인합니다.

    if (isAcceptable) accept() L350 · L383–391

    null이 나올 때까지 백로그를 비웁니다. 새 채널을 논블로킹으로 바꾸고 OP_READ + new Connection()으로 등록합니다.

    if (isValid && isReadable) read(key) L353 · L393–419

    버퍼에 이어 읽고 \n 단위로 잘라 dispatch합니다. -1이면 닫습니다. 아래 시뮬레이터에서 단계별로 볼 수 있습니다.

    if (isValid && isWritable) write(key) L356 · L446–460

    out 대기열을 소켓에 씁니다. 덜 썼으면 그대로 두고, 다 썼으면 OP_WRITE를 끕니다.

    키 하나가 읽기와 쓰기 준비를 동시에 가질 수 있어서 else if가 아니라 if 세 개입니다.

  6. catch (IOException e) → closeConnection(key)L359–362

    try가 키 하나만 감쌉니다. 상대의 RST 같은 오류가 나도 그 연결만 닫히고 루프는 계속 돕니다.

  7. while (running)L337 · L367–373

    running이 true면 1번으로 돌아갑니다. close()가 false로 바꾸고 깨우면 루프를 빠져나와 finally에서 등록된 모든 키 → Selector → 서버 소켓 순서로 닫습니다.

요청 한 줄이 응답이 되기까지

클라이언트가 "hello\n"을 보냈을 때 세 스레드 사이에서 일어나는 일을 순서대로 그렸습니다. 4번 이후 event-loop는 handler를 기다리지 않고 다른 연결을 처리합니다.

read() 안에서 버퍼가 움직이는 모양

write() 안에서 버퍼가 움직이는 모양

      
enqueue()가 응답을 out 대기열에 넣고 write()가 소켓 송신 버퍼로 옮기는 과정입니다. 송신 버퍼에 자리가 모자라면 일부만 쓰고, 남은 위치(position)를 버퍼에 그대로 둔 채 다음 기회에 이어 씁니다. 송신 버퍼는 8칸 또는 16칸으로 줄였습니다. 실제로는 송신 버퍼와 상대 수신 버퍼를 합쳐 수백 KB입니다(예제 7번 실측 393,213바이트).

      
오른쪽 코드는 단계마다 지금 실행 중인 메서드로 바뀝니다. 코드 위에는 어느 스레드가 어떤 경로로 그 메서드에 들어왔는지 표시합니다. 응답이 read()에서 시작해 워커를 거쳐 enqueue()에 도착하는 길도 처음부터 따라갑니다. 줄 번호는 예제 문서 기준입니다.

OP_WRITE는 보낼 게 있을 때만 켠다

      
소켓 송신 버퍼는 평소 거의 비어 있어서 늘 "쓸 수 있음" 상태입니다. OP_WRITE를 켜 두면 할 일이 없어도 select()가 즉시 반환되므로, enqueue()(L443)에서 켜고 write()(L459)에서 끕니다.

코드에서 보이는 주의점

      
학습용 예제라 문제는 아니지만 실무 코드로 옮길 때 고칠 부분입니다.

    

    
    
      
  • 주의 1
    handler가 예외를 던지면 그 연결은 더 응답하지 않는다
    앞 단계가 예외로 끝나면 thenRunAsync로 붙은 뒤 단계는 실행되지 않고 함께 예외로 완료됩니다. 람다 안에서 try/catch로 오류 응답을 만들거나 handle()로 체인을 복구하세요.
    • 
      
  • 주의 2
    accept()의 IOException이 리스닝 소켓을 닫는다
    L359의 catch가 서버 키에도 closeConnection(key)를 적용합니다. "Too many open files" 한 번에 서버가 새 연결을 받지 못하게 됩니다. accept 오류는 따로 처리하는 편이 안전합니다.
    • 
      
  • 주의 3
    \r을 제거하지 않는다
    CRLF를 보내는 클라이언트(telnet 등)에서는 줄 끝에 \r이 붙은 채로 handler에 전달됩니다.
