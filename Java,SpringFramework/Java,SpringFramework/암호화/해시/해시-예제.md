## 1. 예제 개요

비밀번호 유틸을 "흔히 보이는 잘못된 코드"에서 시작해 단계적으로 고치고, 웹훅 서명 검증과 기존 해시 마이그레이션까지 만든다.

| 예제 | 검증하는 개념 | 이론 문서 대응 |
|---|---|---|
| `BadPasswordUtil` | 공유 `MessageDigest`의 경쟁 상태, BigInteger hex 함정, salt 없는 빠른 해시 | 8장 함정 1·3·4·5 |
| `HashUtils` | SHA-256의 결정성·고정 길이·눈사태 효과, 올바른 hex 변환, HMAC 계산 | 3장, 5-1 |
| `BCryptPasswordEncoder` 시연 | 랜덤 salt, `matches`, cost에 따른 속도, 72바이트 제한 | 5-2, 6장, 함정 2·7 |
| `WebhookSigner` | HMAC 서명, 상수 시간 비교 | 5-4, 함정 5·6 |
| `PasswordService` + `LegacySha256PasswordEncoder` | `DelegatingPasswordEncoder`로 레거시 해시를 로그인 시점에 재해시 | 5-3, 6장, 9-1 |

## 3. 잘못된 코드 먼저

실무 레거시에서 자주 보이는 형태다. 한 파일에 문제가 6개 있다.

```java
package com.study.hash;

import java.math.BigInteger;
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;

/** 실무에서 자주 보이는 잘못된 비밀번호 해시 유틸. 따라 쓰지 말 것. */
public final class BadPasswordUtil {

    // 문제 1: 상태를 가진 MessageDigest를 static으로 공유한다.
    private static final MessageDigest MD;

    static {
        try {
            MD = MessageDigest.getInstance("SHA-256");
        } catch (NoSuchAlgorithmException e) {
            throw new IllegalStateException(e);
        }
    }

    private BadPasswordUtil() {
    }

    public static String hash(String password) {
        // 문제 2: salt가 없다. 같은 비밀번호는 모든 사용자에게서 같은 해시가 된다.
        // 문제 3: SHA-256은 빠르다. GPU로 초당 수십억 번 대입할 수 있다.
        // 문제 4: getBytes()가 플랫폼 기본 charset을 쓴다. (Java 17 이하 Windows는 MS949 등)
        byte[] digest = MD.digest(password.getBytes());
        // 문제 5: BigInteger는 숫자라서 앞자리 0을 버린다. 64글자가 아닌 63글자 이하가 나올 수 있다.
        return new BigInteger(1, digest).toString(16);
    }

    public static boolean check(String password, String stored) {
        // 문제 6: String.equals는 상수 시간 비교가 아니다.
        return hash(password).equals(stored);
    }
}
```

| 문제 | 실제로 일어나는 일 | 이론 |
|---|---|---|
| 1. static `MessageDigest` 공유 | 8스레드 × 2만 번 실행 → **틀린 값 84,356건, 예외 1,910건** | 함정 3 |
| 2. salt 없음 | 같은 비밀번호를 쓰는 사용자들이 DB에서 같은 값으로 보인다. 레인보우 테이블로 즉시 찾힌다 | 함정 1 |
| 3. 빠른 해시 | 같은 PC에서 SHA-256 100만 번에 88ms. 공격자도 그만큼 빠르게 대입한다 | 함정 1 |
| 4. `getBytes()` 기본 charset | Java 17 이하 한국어 Windows에서는 MS949 → 한글 비밀번호 해시가 다른 시스템과 다르다 | 함정 4 |
| 5. `BigInteger.toString(16)` | `"user1"`의 해시가 63글자로 나온다(앞자리 `0` 손실) | 함정 4 |
| 6. `String.equals` | 비교 시간으로 몇 글자가 맞았는지 새어 나간다 | 함정 5 |

문제 1에서 실제로 나온 예외(경쟁 상태라서 실행마다 다르게 나온다):

```
Caused by: java.lang.ArrayIndexOutOfBoundsException: arraycopy: last destination index 120 out of bounds for byte[64]
	at java.base/java.lang.System.arraycopy(Native Method)
	at java.base/sun.security.provider.DigestBase.engineUpdate(DigestBase.java:117)
	at java.base/sun.security.provider.SHA2.implDigest(SHA2.java:110)
	at java.base/sun.security.provider.DigestBase.engineDigest(DigestBase.java:205)
	...
	at java.base/java.security.MessageDigest.digest(MessageDigest.java:457)

```

`byte[64]`는 SHA-256의 블록 버퍼(64바이트)다. 한 스레드가 버퍼 위치를 옮기는 사이 다른 스레드가 그 위치에 쓰려다 범위를 벗어났다. [이론 5-1](./해시-이론.md#5-1-일반-해시sha-256가-계산되는-방식)의 "내부 버퍼"가 실제로 공유되었다는 증거다.

## 4. 개선된 코드

### 1단계: 해시 계산을 안전하게 — `HashUtils`

- 호출마다 `MessageDigest.getInstance()` → **문제 1 해결**
- `StandardCharsets.UTF_8` 명시 → **문제 4 해결**
- `HexFormat`으로 바이트당 정확히 2글자 → **문제 5 해결**

전체 코드는 5장에 있다. 핵심 부분:

```java
public static byte[] sha256(String input) {
    try {
        MessageDigest md = MessageDigest.getInstance("SHA-256");
        return md.digest(input.getBytes(StandardCharsets.UTF_8));
    } catch (NoSuchAlgorithmException e) {
        throw new IllegalStateException(e);
    }
}

public static String toHex(byte[] bytes) {
    return HexFormat.of().formatHex(bytes);
}
```

Java 8 대체 코드 (`HexFormat`이 없음):

```java
public static String toHex(byte[] bytes) {
    StringBuilder sb = new StringBuilder(bytes.length * 2);
    for (byte b : bytes) {
        // %02x: 항상 2자리, 앞을 0으로 채운다. byte가 음수여도 Formatter가 하위 8비트로 출력한다.
        sb.append(String.format("%02x", b));
    }
    return sb.toString();
}

public static byte[] fromHex(String hex) {
    if (hex.length() % 2 != 0) {
        throw new IllegalArgumentException("hex 길이는 짝수여야 한다");
    }
    byte[] out = new byte[hex.length() / 2];
    for (int i = 0; i < out.length; i++) {
        int hi = Character.digit(hex.charAt(i * 2), 16);
        int lo = Character.digit(hex.charAt(i * 2 + 1), 16);
        if (hi < 0 || lo < 0) {
            throw new IllegalArgumentException("hex가 아닌 문자: " + hex);
        }
        out[i] = (byte) ((hi << 4) | lo);
    }
    return out;
}
// Java 7이라면 StandardCharsets(Java 7+)는 쓸 수 있고, multi-catch도 Java 7부터 가능하다.
```

**좋아진 점**: 결과가 스레드·OS·JDK 버전과 무관하게 같아진다. 하지만 이것은 여전히 **빠른 해시**다. 무결성 확인이나 토큰 해시에는 충분하지만 비밀번호에는 쓰면 안 된다.

### 2단계: 비밀번호는 비밀번호 해시로 — `BCryptPasswordEncoder`

```java
PasswordEncoder encoder = new BCryptPasswordEncoder(12);
String stored = encoder.encode(rawPassword);       // 가입: 매번 다른 salt
boolean ok = encoder.matches(rawPassword, stored); // 로그인: equals 금지
```

- 사용자별 랜덤 salt가 자동으로 붙는다 → **문제 2 해결**
- strength 12 = 한 번에 약 150ms → **문제 3 해결** (공격자의 대입 속도가 SHA-256 대비 백만 배 이상 느려진다)
- `matches`가 내부에서 상수 시간 비교 → **문제 6 해결**

**좋아진 점**: DB가 유출돼도 비밀번호 하나를 맞히려면 사용자마다 따로, 한 번에 150ms씩 계산해야 한다.
**남은 문제**: 이미 DB에 쌓인 SHA-256 값은 원문을 모르니 bcrypt로 바꿀 수 없다.

### 3단계: 기존 데이터 마이그레이션 — `DelegatingPasswordEncoder`

평문을 알 수 있는 유일한 순간은 **로그인 성공 직후**다([이론 5-3](./해시-이론.md#5-3-spring-security에서-로그인할-때-일어나는-일)). 그때 새 형식으로 다시 저장한다.

```java
Map<String, PasswordEncoder> encoders = new HashMap<>();
encoders.put("bcrypt", new BCryptPasswordEncoder(12));
DelegatingPasswordEncoder delegating = new DelegatingPasswordEncoder("bcrypt", encoders);
// {id} 접두어가 없는 기존 값 → 레거시 SHA-256 인코더로 검증만
delegating.setDefaultPasswordEncoderForMatches(new LegacySha256PasswordEncoder());
```

```java
if (encoder.matches(rawPassword, stored) && encoder.upgradeEncoding(stored)) {
    userStore.put(username, encoder.encode(rawPassword)); // "{bcrypt}$2a$12$..."
}
```

- 접두어 없는 값 → `upgradeEncoding` true → bcrypt로 교체
- `{bcrypt}$2a$10$...` → id는 같지만 cost 10 < 12 → `BCryptPasswordEncoder.upgradeEncoding` true → cost 12로 교체
- 없는 사용자도 더미 해시로 `matches`를 호출해 응답 시간을 맞춘다(Spring Security `DaoAuthenticationProvider`와 같은 방식)

**좋아진 점**: 서비스를 멈추지 않고, 사용자에게 비밀번호 재설정을 요구하지 않고 형식을 바꿀 수 있다. 다음에 Argon2로 바꿀 때도 `idForEncode`만 바꾸면 된다.

Spring Security를 쓴다면 이 로직을 직접 짤 필요 없이 `UserDetailsPasswordService`만 구현하면 된다. 위 코드는 그 내부 동작을 보여 주는 용도다.

### 4단계: 웹훅 서명 — `WebhookSigner`

- `Mac.getInstance("HmacSHA256")` → 키 없이는 위조할 수 없다. 길이 확장 공격도 통하지 않는다(함정 6)
- 받은 서명을 바이트로 디코드해서 `MessageDigest.isEqual()` → 상수 시간 비교(함정 5). 대소문자 차이(`AB` vs `ab`)에도 흔들리지 않는다
- 형식이 잘못된 서명은 예외를 던지지 않고 false → 컨트롤러에서 401로 바꾸기 쉽다

## 5. 전체 코드

### HashUtils.java

```java
package com.study.hash;

import java.nio.charset.StandardCharsets;
import java.security.InvalidKeyException;
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.util.HexFormat;

import javax.crypto.Mac;
import javax.crypto.spec.SecretKeySpec;

public final class HashUtils {

    private HashUtils() {
    }

    public static byte[] sha256(String input) {
        try {
            // MessageDigest는 update()로 받은 바이트를 내부에 쌓아 두는 상태(stateful) 객체다.
            // 여러 스레드가 공유하면 입력이 섞이므로 호출마다 새로 얻는다. getInstance 비용은 해시 계산보다 작다.
            MessageDigest md = MessageDigest.getInstance("SHA-256");
            // 해시는 문자열이 아니라 바이트에 대해 계산된다. 인코딩이 다르면 바이트가 달라지고 해시도 달라지므로 UTF-8을 명시한다.
            return md.digest(input.getBytes(StandardCharsets.UTF_8));
        } catch (NoSuchAlgorithmException e) {
            // Java SE 스펙상 SHA-256은 모든 JDK가 반드시 제공해야 하므로 실제로는 도달하지 않는다.
            throw new IllegalStateException(e);
        }
    }

    public static String sha256Hex(String input) {
        return toHex(sha256(input));
    }

    public static byte[] hmacSha256(byte[] key, String message) {
        try {
            // Mac도 MessageDigest처럼 상태 객체라 공유하지 않는다.
            Mac mac = Mac.getInstance("HmacSHA256");
            mac.init(new SecretKeySpec(key, "HmacSHA256"));
            return mac.doFinal(message.getBytes(StandardCharsets.UTF_8));
        } catch (NoSuchAlgorithmException | InvalidKeyException e) {
            throw new IllegalStateException(e);
        }
    }

    public static String toHex(byte[] bytes) {
        // HexFormat(Java 17+)은 바이트마다 정확히 2글자를 만든다. 앞자리 0이 사라지지 않는다.
        return HexFormat.of().formatHex(bytes);
    }

    public static int differentBits(byte[] a, byte[] b) {
        if (a.length != b.length) {
            throw new IllegalArgumentException("길이가 다른 해시는 비교할 수 없다");
        }
        int count = 0;
        for (int i = 0; i < a.length; i++) {
            // byte는 부호가 있으므로 & 0xFF로 하위 8비트만 남긴 뒤 센다.
            count += Integer.bitCount((a[i] ^ b[i]) & 0xFF);
        }
        return count;
    }
}
```

### WebhookSigner.java

```java
package com.study.hash;

import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.util.HexFormat;

public final class WebhookSigner {

    private final byte[] secretKey;

    public WebhookSigner(String secret) {
        this.secretKey = secret.getBytes(StandardCharsets.UTF_8);
    }

    public String sign(String body) {
        return HashUtils.toHex(HashUtils.hmacSha256(secretKey, body));
    }

    public boolean verify(String body, String receivedSignatureHex) {
        if (receivedSignatureHex == null) {
            return false;
        }
        byte[] received;
        try {
            // 문자열끼리 비교하지 않고 바이트로 되돌려 비교한다. 대소문자 차이(AB vs ab)에 흔들리지 않는다.
            received = HexFormat.of().parseHex(receivedSignatureHex);
        } catch (IllegalArgumentException e) {
            return false;
        }
        byte[] expected = HashUtils.hmacSha256(secretKey, body);
        // String.equals는 처음 다른 글자에서 바로 반환하므로, 응답 시간으로 "앞에서 몇 글자가 맞았는지"가 새어 나간다.
        // MessageDigest.isEqual은 길이가 같으면 끝까지 비교하는 상수 시간(constant-time) 비교다.
        return MessageDigest.isEqual(expected, received);
    }
}
```

### LegacySha256PasswordEncoder.java

```java
package com.study.hash;

import java.security.MessageDigest;
import java.util.HexFormat;

import org.springframework.security.crypto.password.PasswordEncoder;

/**
 * 기존 DB에 남아 있는 "salt 없는 SHA-256 hex" 값을 검증만 하기 위한 인코더.
 * 새 비밀번호를 이 형식으로 저장하면 안 되므로 encode는 막아 둔다.
 */
public final class LegacySha256PasswordEncoder implements PasswordEncoder {

    @Override
    public String encode(CharSequence rawPassword) {
        throw new UnsupportedOperationException("레거시 형식으로는 새로 저장하지 않는다");
    }

    @Override
    public boolean matches(CharSequence rawPassword, String encodedPassword) {
        if (rawPassword == null || encodedPassword == null) {
            return false;
        }
        byte[] expected;
        try {
            expected = HexFormat.of().parseHex(encodedPassword);
        } catch (IllegalArgumentException e) {
            return false;
        }
        byte[] actual = HashUtils.sha256(rawPassword.toString());
        return MessageDigest.isEqual(actual, expected);
    }
}
```

### PasswordService.java

```java
package com.study.hash;

import java.util.HashMap;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.DelegatingPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;

public class PasswordService {

    private final PasswordEncoder encoder;
    // 예제를 단순하게 하려고 DB 대신 Map을 쓴다. 값은 password 컬럼에 들어갈 문자열 그대로다.
    private final Map<String, String> userStore = new ConcurrentHashMap<>();
    // 없는 사용자로 로그인할 때도 같은 비용의 해시 비교를 하기 위한 더미 값
    private final String dummyHash;

    public PasswordService(PasswordEncoder encoder) {
        this.encoder = encoder;
        this.dummyHash = encoder.encode("dummy-password-for-timing");
    }

    public static PasswordEncoder createEncoder() {
        Map<String, PasswordEncoder> encoders = new HashMap<>();
        // strength(cost) 12 = 2^12번 반복. 값을 올리면 기존 해시는 upgradeEncoding()이 true가 되어 로그인 때 재해시된다.
        encoders.put("bcrypt", new BCryptPasswordEncoder(12));
        DelegatingPasswordEncoder delegating = new DelegatingPasswordEncoder("bcrypt", encoders);
        // {id} 접두어가 없는 기존 값은 레거시 SHA-256으로 보고 검증만 한다.
        // 이 설정이 없으면 접두어 없는 값에서 IllegalArgumentException이 난다.
        delegating.setDefaultPasswordEncoderForMatches(new LegacySha256PasswordEncoder());
        return delegating;
    }

    public void register(String username, String rawPassword) {
        userStore.put(username, encoder.encode(rawPassword));
    }

    /** 마이그레이션 이전부터 있던 데이터를 흉내 내기 위한 메서드 */
    public void putRaw(String username, String storedValue) {
        userStore.put(username, storedValue);
    }

    public String storedValue(String username) {
        return userStore.get(username);
    }

    public boolean login(String username, String rawPassword) {
        String stored = userStore.get(username);
        if (stored == null) {
            // 바로 false를 반환하면 "없는 사용자"는 수 ms, "있는 사용자"는 수백 ms가 걸려 계정 존재 여부가 드러난다.
            encoder.matches(rawPassword, dummyHash);
            return false;
        }
        if (!encoder.matches(rawPassword, stored)) {
            return false;
        }
        // 평문 비밀번호를 가진 순간은 로그인 성공 직후뿐이다. 이때만 새 형식으로 다시 저장할 수 있다.
        if (encoder.upgradeEncoding(stored)) {
            userStore.put(username, encoder.encode(rawPassword));
        }
        return true;
    }
}
```

결과 읽기:

- **1번**: 한 글자 차이로 256비트 중 118비트(46%)가 바뀌었다. 입력이 1글자든 100만 글자든 출력은 64글자다.
- **3번**: 16만 번 중 절반 이상이 틀렸다. 예외가 1,910건이라 **틀린 결과 대부분은 예외 없이 조용히 반환됐다**는 점이 더 위험하다.
- **4번**: SHA-256 100만 번(88ms)이 bcrypt(10) 세 번(37ms × 3) 정도와 같다.
- **5번**: 60글자 = `$2a$` + `10$` + salt 22자 + 해시 31자. 대소문자만 다른 `Password123`은 false다.
- **6번**: 서명을 대문자로 보내도 바이트로 디코드해서 비교하므로 true다. 금액을 바꾸거나 다른 키로 서명하면 false다.
- **7번**: 접두어 없던 alice와 cost 10이던 bob이 **로그인 한 번으로** 모두 `{bcrypt}$2a$12$`가 됐다. 틀린 비밀번호로 시도할 때는 바뀌지 않았다.
- **8번**: `encode`는 73바이트를 거부했지만 **`matches`는 73바이트 입력에 true를 반환했다**. 저장된 72바이트 뒤에 아무 문자나 붙여도 통과한다는 뜻이다. 그래서 길이 검증은 라이브러리에 맡기지 말고 API 입구에서 해야 한다([이론 함정 7](./해시-이론.md#함정-7-bcrypt는-72바이트까지만-본다)).

## 8. 변형 실습

1. **`PasswordService.createEncoder()`의 `setDefaultPasswordEncoderForMatches(...)` 줄을 지우면?**
   alice(접두어 없는 레거시 값)로 로그인할 때 7장 마지막의 `IllegalArgumentException`이 난다. Spring Security 5.0으로 올리면서 기존 DB를 그대로 둔 프로젝트에서 실제로 생기는 장애다. `UPDATE member SET password = '{SHA-256}' || password`처럼 데이터에 접두어를 붙이는 방법과 비교해 보자. (주의: Spring의 `{SHA-256}` id는 `StandardPasswordEncoder`라서 salt 없는 순수 SHA-256 hex와 **형식이 다르다**. 그대로 붙이면 검증이 실패한다. 직접 실행해서 확인해 보자.)

2. **`WebhookSigner.verify`를 `sign(body).equals(receivedSignatureHex)`로 바꾸면?**
   7장의 JUnit 테스트는 모두 통과하고, 데모에서는 "대문자 서명 검증"만 false로 바뀐다. 그런데 보안상으로는 타이밍 공격에 열린다. 테스트가 통과했다고 안전한 것은 아니라는 예다. 서명 비교 시간을 `System.nanoTime()`으로 1만 번씩 재서, 첫 글자가 틀린 경우와 마지막 글자만 틀린 경우의 평균 차이를 측정해 보자(JIT 때문에 차이가 작게 나올 수 있다).

3. **`HashDemo.speedComparison()`에 `new BCryptPasswordEncoder(14)`를 추가하면?**
   cost가 1 오를 때마다 시간이 2배가 되는지 확인한다(10 → 12에서 실측 약 4배). 로그인 API의 목표 응답 시간(예: 해시에 250ms 이하)과 서버 CPU 코어 수를 생각해서, 동시 로그인 100건이 들어오면 몇 초가 걸리는지 계산해 보자. cost를 무조건 올리는 게 답이 아닌 이유가 보인다(로그인 API가 CPU를 고갈시키는 DoS 경로가 된다).
