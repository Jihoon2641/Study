# 직렬화와 역직렬화 — 예제

관련 문서: [이론](./직렬화-이론.md)

---

## 1. 예제 개요

잔액이 음수가 될 수 없는 `Account`, 세션에 저장할 `LoginUser`, 싱글턴 `Settings`를 만든다. 흔한 잘못된 코드로 사고를 **재현**한 뒤, 단계적으로 고치고 JUnit으로 증명한다.

| 예제 | 검증하는 개념 | 이론 문서 |
|---|---|---|
| 스트림의 UID 바꿔치기 | `serialVersionUID` 불일치 → `InvalidClassException` | 8.1 |
| `LegacyAccount` → `Account` | `transient` 필드 초기화 식 미실행, `readObject`로 복원 | 5.2, 8.2 |
| `LegacyAccount` → `Account` / `AccountRecord` | 역직렬화는 생성자를 우회한다, `readObject` 검증, record는 정식 생성자를 거친다 | 5.2, 6, 8.3 |
| `LoginUserBad` → `LoginUser` | 그래프 안의 비직렬화 필드 → `NotSerializableException` | 5.1, 8.4 |
| `SettingsBad` → `Settings` / `EnumSettings` | 역직렬화는 싱글턴을 깨뜨린다, `readResolve`와 enum | 6, 8.5 |
| 역직렬화 필터 | 허용 목록에 없는 클래스 거부 | 8.6 |

## 3. 잘못된 코드 먼저

### 3-1. `LegacyAccount` — UID 없음, 검증은 생성자에만, `transient` 필드 초기화

```java
package study.serialization.account;

import java.io.Serializable;

// serialVersionUID가 없다 → JDK가 클래스 구조로 자동 계산한다
public class LegacyAccount implements Serializable {

    // 역직렬화가 생성자를 부르는지 세어보기 위한 카운터 (static은 직렬화되지 않는다)
    public static int constructorCalls = 0;

    private final String owner;
    private final long balance;

    // 선언과 함께 초기화해도, 이 식은 생성자 안으로 컴파일된다
    private transient StringBuilder history = new StringBuilder("created;");

    public LegacyAccount(String owner, long balance) {
        if (balance < 0) {
            throw new IllegalArgumentException("balance must be >= 0: " + balance);
        }
        constructorCalls++;
        this.owner = owner;
        this.balance = balance;
    }

    public String getOwner() {
        return owner;
    }

    public long getBalance() {
        return balance;
    }

    public StringBuilder getHistory() {
        return history;
    }
}
```

문제점:

1. 역직렬화 시 생성자가 호출되지 않아 `balance >= 0` 검증이 우회된다. 바이트를 조작하면 음수 잔액 객체가 만들어진다 (이론 8.3).
2. `history`가 역직렬화 후 `null`이다. `getHistory().append(...)`에서 NPE (이론 8.2).
3. UID 미선언. 메서드 하나만 추가해도 저장된 데이터를 못 읽는다 (이론 8.1).

### 3-2. `LoginUserBad` — 세션 객체가 서비스를 들고 있다

```java

package study.serialization.session;
```

## 4. 개선된 코드

### 4-1. `Account` — UID 선언 + `readObject`로 검증·복원

```java
package study.serialization.account;

import java.io.IOException;
import java.io.InvalidObjectException;
import java.io.ObjectInputStream;
import java.io.Serial;
import java.io.Serializable;

public final class Account implements Serializable {

    // 명시적 버전: 메서드·필드 추가 같은 호환 가능한 변경 후에도 기존 데이터를 읽을 수 있다
    @Serial
    private static final long serialVersionUID = 1L;

    private final String owner;
    private final long balance;
    private transient StringBuilder history;

    public Account(String owner, long balance) {
        validate(owner, balance);
        this.owner = owner;
        this.balance = balance;
        this.history = new StringBuilder("created;");
    }

    // 역직렬화는 생성자를 거치지 않으므로, 생성자와 같은 검증을 여기서 한 번 더 한다
    @Serial
    private void readObject(ObjectInputStream in) throws IOException, ClassNotFoundException {
        in.defaultReadObject();
        try {
            validate(owner, balance);
        } catch (IllegalArgumentException e) {
            // readObject는 IOException 계열로 실패를 알리는 것이 계약이다
            throw new InvalidObjectException(e.getMessage());
        }
        // 필드 초기화 식이 실행되지 않으므로 transient 필드는 직접 다시 만든다
        this.history = new StringBuilder("restored;");
    }

    private static void validate(String owner, long balance) {
        if (owner == null || owner.isBlank()) {
            throw new IllegalArgumentException("owner is required");
        }
        if (balance < 0) {
            throw new IllegalArgumentException("balance must be >= 0: " + balance);
        }
    }

    public String getOwner() {
        return owner;
    }

    public long getBalance() {
        return balance;
    }

    public StringBuilder getHistory() {
        return history;
    }
}
```

**좋아진 점**
- 조작된 바이트는 `InvalidObjectException`으로 거부된다.
- `history`가 `null`이 아니다.
- UID가 고정되어 메서드를 추가해도 기존 데이터를 읽는다.

> **Java 8 대응**: `@Serial`(Java 14+)을 지운다. `owner.isBlank()`(Java 11+)는 `owner.trim().isEmpty()`로 바꾼다. `readObject` 훅 규칙은 Java 1.1부터 같다. 주의할 점은 **`@Serial`이 없으면 메서드 이름·시그니처 오타를 아무도 알려주지 않는다**는 것이다. 오타가 나면 JDK가 훅을 조용히 무시한다.

### 4-2. `AccountRecord` — record로 검증을 한 곳에 (Java 16+)

```java
package study.serialization.account;

import java.io.Serializable;

// record는 역직렬화 때 정식 생성자를 호출하므로 readObject 없이도 검증이 적용된다
public record AccountRecord(String owner, long balance) implements Serializable {

    public AccountRecord {
        if (owner == null || owner.isBlank()) {
            throw new IllegalArgumentException("owner is required");
        }
        if (balance < 0) {
            throw new IllegalArgumentException("balance must be >= 0: " + balance);
        }
    }
}
```

**좋아진 점**: 검증 코드가 생성자 한 곳에만 있다. 역직렬화 경로를 따로 신경 쓸 필요가 없다.

> **Java 8~15 대응**: record가 없으므로 4-1처럼 `readObject`를 쓰거나, 이펙티브 자바 아이템 90의 **직렬화 프록시 패턴**을 쓴다. 불변 데이터 클래스라면 4-1 방식으로 충분하다.

### 4-3. `LoginUser` — 세션에는 데이터만

```java
package study.serialization.session;

import java.io.Serial;
import java.io.Serializable;

// 세션·캐시에 넣는 객체는 식별자와 표시용 데이터만 가진다. 동작(포인트 조회)은 서비스에서 한다
public final class LoginUser implements Serializable {

    @Serial
    private static final long serialVersionUID = 1L;

    private final String userId;
    private final String name;

    public LoginUser(String userId, String name) {
        this.userId = userId;
        this.name = name;
    }

    public String getUserId() {
        return userId;
    }

    public String getName() {
        return name;
    }
}
```

```java
// 호출하는 쪽: 필요할 때 서비스로 조회한다
long point = pointService.currentPoint(loginUser.getUserId());
```

**좋아진 점**: 객체 그래프가 `String` 두 개뿐이라 직렬화가 항상 성공한다. 세션 크기도 작아진다.

> `PointService`를 꼭 필드로 가져야 한다면 `private transient PointService pointService;`로 빼고, 역직렬화 후 다시 주입하는 코드가 필요하다. 세션 객체에서는 권하지 않는다.

### 4-4. `Settings` — `readResolve`로 싱글턴 유지

```java
package study.serialization.singleton;

import java.io.Serial;
import java.io.Serializable;

public final class Settings implements Serializable {

    @Serial
    private static final long serialVersionUID = 1L;

    public static final Settings INSTANCE = new Settings();

    // transient: 스트림의 값은 어차피 버려지므로 저장하지 않는다 (이펙티브 자바 아이템 89 권고)
    private transient String mode = "normal";

    private Settings() {
    }

    // 역직렬화로 만들어진 새 객체를 버리고 기존 싱글턴으로 교체한다
    @Serial
    private Object readResolve() {
        return INSTANCE;
    }

    public String getMode() {
        return mode;
    }

    public void setMode(String mode) {
        this.mode = mode;
    }
}
```

### 4-5. `EnumSettings` — 가장 단순한 해법

```java
package study.serialization.singleton;

// enum은 상수 이름만 직렬화되고, 역직렬화 때 JDK가 기존 상수를 찾아 돌려준다
public enum EnumSettings {
    INSTANCE;

    private String mode = "normal";

    public String getMode() {
        return mode;
    }

    public void setMode(String mode) {
        this.mode = mode;
    }
}
```

**좋아진 점**: `readResolve`를 잊을 위험이 없다. enum의 필드(`mode`)는 직렬화되지 않고, 역직렬화 결과가 항상 현재 JVM의 `INSTANCE`다.

### 4-6. 역직렬화 필터 — 허용 목록 (Java 9+)

신뢰할 수 없는 바이트를 어쩔 수 없이 읽어야 할 때, 허용할 클래스만 지정한다.

```java
ObjectInputFilter filter = ObjectInputFilter.Config.createFilter(
        "study.serialization.account.Account;java.base/*;!*");   // Account와 JDK 기본 클래스만 허용, 나머지 거부

try (ObjectInputStream in = new ObjectInputStream(new ByteArrayInputStream(bytes))) {
    in.setObjectInputFilter(filter);
    Object obj = in.readObject();   // 허용 목록 밖의 클래스면 InvalidClassException
}
```

> **Java 8 대응**: 8u121 이상에서 `sun.misc.ObjectInputFilter`로 같은 기능을 쓸 수 있다(내부 API). JVM 전역으로는 `-Djdk.serialFilter=...` 시스템 프로퍼티를 쓴다. 8u121 미만은 `ObjectInputStream`을 상속해 `resolveClass`를 재정의하는 방식으로 막았다.

## 5. 전체 코드

### `SerializationUtils.java`

```java
package study.serialization;

import java.io.ByteArrayInputStream;
import java.io.ByteArrayOutputStream;
import java.io.IOException;
import java.io.ObjectInputFilter;
import java.io.ObjectInputStream;
import java.io.ObjectOutputStream;
import java.io.UncheckedIOException;
import java.nio.ByteBuffer;

public final class SerializationUtils {

    private SerializationUtils() {
    }

    public static byte[] serialize(Object obj) throws IOException {
        ByteArrayOutputStream bos = new ByteArrayOutputStream();
        try (ObjectOutputStream out = new ObjectOutputStream(bos)) {
            out.writeObject(obj);
        }
        return bos.toByteArray();
    }

    // 테스트에서 InvalidClassException 등 실제 예외 타입을 확인하려고 감싸지 않고 던진다
    @SuppressWarnings("unchecked")
    public static <T> T deserialize(byte[] bytes) throws IOException, ClassNotFoundException {
        try (ObjectInputStream in = new ObjectInputStream(new ByteArrayInputStream(bytes))) {
            return (T) in.readObject();
        }
    }

    @SuppressWarnings("unchecked")
    public static <T> T deserialize(byte[] bytes, ObjectInputFilter filter)
            throws IOException, ClassNotFoundException {
        try (ObjectInputStream in = new ObjectInputStream(new ByteArrayInputStream(bytes))) {
            in.setObjectInputFilter(filter);
            return (T) in.readObject();
        }
    }

    // 직렬화 형식을 몰라도 테스트를 쓸 수 있도록 하는 원형 왕복 도우미
    public static <T> T roundTrip(T obj) {
        try {
            return deserialize(serialize(obj));
        } catch (IOException e) {
            throw new UncheckedIOException(e);
        } catch (ClassNotFoundException e) {
            throw new IllegalStateException(e);
        }
    }

    /**
     * 바이트 안에서 8바이트 long 값을 찾아 다른 값으로 바꾼다 (공격자의 스트림 조작 재현).
     * 스트림은 [클래스 정보(UID 포함)] → [필드 값] 순서이므로
     * UID를 바꾸려면 앞에서부터(fromEnd=false), 필드 값을 바꾸려면 뒤에서부터(fromEnd=true) 찾는다.
     */
    public static byte[] replaceLong(byte[] bytes, long from, long to, boolean fromEnd) {
        byte[] pattern = ByteBuffer.allocate(Long.BYTES).putLong(from).array();
        byte[] replacement = ByteBuffer.allocate(Long.BYTES).putLong(to).array();
        int last = bytes.length - pattern.length;
        for (int n = 0; n <= last; n++) {
            int i = fromEnd ? last - n : n;
            if (matches(bytes, i, pattern)) {
                byte[] copy = bytes.clone();
                System.arraycopy(replacement, 0, copy, i, replacement.length);
                return copy;
            }
        }
        throw new IllegalArgumentException("pattern not found: " + from);
    }

    private static boolean matches(byte[] bytes, int offset, byte[] pattern) {
        for (int j = 0; j < pattern.length; j++) {
            if (bytes[offset + j] != pattern[j]) {
                return false;
            }
        }
        return true;
    }
}
```

> Java 8 대응: `ObjectInputFilter`를 쓰는 `deserialize(byte[], ObjectInputFilter)` 메서드를 제거한다. 나머지는 Java 7 문법(try-with-resources)까지만 쓴다.

### `SerializationDemo.java`

```java
package study.serialization;

import study.serialization.account.Account;
import study.serialization.account.AccountRecord;
import study.serialization.account.LegacyAccount;
import study.serialization.session.LoginUserBad;
import study.serialization.session.PointService;
import study.serialization.singleton.EnumSettings;
import study.serialization.singleton.Settings;
import study.serialization.singleton.SettingsBad;

import java.io.ObjectInputFilter;

public class SerializationDemo {

    public static void main(String[] args) throws Exception {
        System.out.println("== 1. UID 불일치");
        byte[] accountBytes = SerializationUtils.serialize(new Account("kim", 100));
        byte[] uidChanged = SerializationUtils.replaceLong(accountBytes, 1L, 2L, false);
        printFailure(() -> SerializationUtils.deserialize(uidChanged));

        System.out.println("== 2. 생성자 우회 / transient");
        LegacyAccount legacy = new LegacyAccount("kim", 100);
        LegacyAccount legacyCopy = SerializationUtils.roundTrip(legacy);
        System.out.println("constructorCalls = " + LegacyAccount.constructorCalls);
        System.out.println("legacy history = " + legacyCopy.getHistory());
        System.out.println("account history = " + SerializationUtils.roundTrip(new Account("kim", 100)).getHistory());

        System.out.println("== 3. 바이트 조작으로 불변식 깨기");
        byte[] legacyBytes = SerializationUtils.serialize(legacy);
        LegacyAccount hacked = SerializationUtils.deserialize(
                SerializationUtils.replaceLong(legacyBytes, 100L, -1L, true));
        System.out.println("LegacyAccount balance = " + hacked.getBalance());
        printFailure(() -> SerializationUtils.deserialize(
                SerializationUtils.replaceLong(accountBytes, 100L, -1L, true)));
        byte[] recordBytes = SerializationUtils.serialize(new AccountRecord("kim", 100));
        printFailure(() -> SerializationUtils.deserialize(
                SerializationUtils.replaceLong(recordBytes, 100L, -1L, true)));

        System.out.println("== 4. 비직렬화 필드");
        printFailure(() -> SerializationUtils.serialize(new LoginUserBad("u1", "kim", new PointService())));

        System.out.println("== 5. 싱글턴");
        System.out.println("SettingsBad same? " + (SerializationUtils.roundTrip(SettingsBad.INSTANCE) == SettingsBad.INSTANCE));
        System.out.println("Settings same? " + (SerializationUtils.roundTrip(Settings.INSTANCE) == Settings.INSTANCE));
        System.out.println("EnumSettings same? " + (SerializationUtils.roundTrip(EnumSettings.INSTANCE) == EnumSettings.INSTANCE));

        System.out.println("== 6. 역직렬화 필터");
        ObjectInputFilter onlyAccount = ObjectInputFilter.Config.createFilter(
                "study.serialization.account.Account;java.base/*;!*");
        System.out.println("Account allowed: " + SerializationUtils.<Account>deserialize(accountBytes, onlyAccount).getBalance());
        printFailure(() -> SerializationUtils.deserialize(legacyBytes, onlyAccount));
    }

    private static void printFailure(ThrowingRunnable action) {
        try {
            action.run();
            System.out.println("(예외 없음)");
        } catch (Exception e) {
            System.out.println(e.getClass().getName() + ": " + e.getMessage());
        }
    }

    @FunctionalInterface
    private interface ThrowingRunnable {
        void run() throws Exception;
```

### `SerializationTest.java`

```java
package study.serialization;

import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Nested;
import org.junit.jupiter.api.Test;
import study.serialization.account.Account;
import study.serialization.account.AccountRecord;
import study.serialization.account.LegacyAccount;
import study.serialization.session.LoginUser;
import study.serialization.session.LoginUserBad;
import study.serialization.session.PointService;
import study.serialization.singleton.EnumSettings;
import study.serialization.singleton.Settings;
import study.serialization.singleton.SettingsBad;

import java.io.InvalidClassException;
import java.io.InvalidObjectException;
import java.io.NotSerializableException;
import java.io.ObjectInputFilter;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

class SerializationTest {

    @Nested
    @DisplayName("기본 동작")
    class Basics {

        @Test
        @DisplayName("역직렬화 결과는 값이 같은 다른 객체다")
        void copyIsDifferentObject() {
            Account original = new Account("kim", 100);

            Account copy = SerializationUtils.roundTrip(original);

            assertThat(copy).isNotSameAs(original);
            assertThat(copy.getOwner()).isEqualTo("kim");
            assertThat(copy.getBalance()).isEqualTo(100);
        }
    }

    @Nested
    @DisplayName("serialVersionUID (이론 8.1)")
    class VersionUid {

        @Test
        @DisplayName("선언한 UID가 클래스 메타데이터에 그대로 쓰인다")
        void declaredUidIsUsed() {
            long uid = java.io.ObjectStreamClass.lookup(Account.class).getSerialVersionUID();

            assertThat(uid).isEqualTo(1L);
        }

        @Test
        @DisplayName("스트림의 UID와 클래스의 UID가 다르면 InvalidClassException")
        void uidMismatchFails() throws Exception {
            byte[] bytes = SerializationUtils.serialize(new Account("kim", 100));
            // 클래스 정보가 필드 값보다 앞에 있으므로 첫 번째 1L이 UID다
            byte[] uidChanged = SerializationUtils.replaceLong(bytes, 1L, 2L, false);

            assertThatThrownBy(() -> SerializationUtils.deserialize(uidChanged))
                    .isInstanceOf(InvalidClassException.class)
                    .hasMessageContaining("local class incompatible");
        }
    }

    @Nested
    @DisplayName("생성자 우회와 transient (이론 8.2, 8.3)")
    class ConstructorBypass {

        @BeforeEach
        void resetCounter() {
            LegacyAccount.constructorCalls = 0;
        }

        @Test
        @DisplayName("역직렬화는 Serializable 클래스의 생성자를 호출하지 않는다")
        void constructorIsNotCalled() {
            LegacyAccount original = new LegacyAccount("kim", 100);

            SerializationUtils.roundTrip(original);

            assertThat(LegacyAccount.constructorCalls).isEqualTo(1);
        }

        @Test
        @DisplayName("transient 필드의 초기화 식은 실행되지 않아 null이 된다")
        void transientInitializerIsSkipped() {
            LegacyAccount copy = SerializationUtils.roundTrip(new LegacyAccount("kim", 100));

            assertThat(copy.getHistory()).isNull();
        }

        @Test
        @DisplayName("readObject에서 transient 필드를 다시 만들 수 있다")
        void readObjectRestoresTransient() {
            Account copy = SerializationUtils.roundTrip(new Account("kim", 100));

            assertThat(copy.getHistory()).hasToString("restored;");
        }

        @Test
        @DisplayName("바이트를 조작하면 생성자 검증을 우회해 음수 잔액 객체가 생긴다")
        void tamperingBreaksInvariant() throws Exception {
            byte[] bytes = SerializationUtils.serialize(new LegacyAccount("kim", 100));
            byte[] tampered = SerializationUtils.replaceLong(bytes, 100L, -1L, true);

            LegacyAccount hacked = SerializationUtils.deserialize(tampered);

            assertThat(hacked.getBalance()).isEqualTo(-1L);
        }

        @Test
        @DisplayName("readObject에서 재검증하면 조작된 바이트를 거부한다")
        void readObjectRejectsTampering() throws Exception {
            byte[] bytes = SerializationUtils.serialize(new Account("kim", 100));
            byte[] tampered = SerializationUtils.replaceLong(bytes, 100L, -1L, true);

            assertThatThrownBy(() -> SerializationUtils.deserialize(tampered))
                    .isInstanceOf(InvalidObjectException.class)
                    .hasMessageContaining("balance must be >= 0");
        }

        @Test
        @DisplayName("record는 역직렬화 때 정식 생성자를 거치므로 조작된 바이트를 거부한다")
        void recordRejectsTampering() throws Exception {
            byte[] bytes = SerializationUtils.serialize(new AccountRecord("kim", 100));
            byte[] tampered = SerializationUtils.replaceLong(bytes, 100L, -1L, true);

            // 생성자가 던진 IllegalArgumentException이 InvalidObjectException으로 감싸진다
            assertThatThrownBy(() -> SerializationUtils.deserialize(tampered))
                    .isInstanceOf(InvalidObjectException.class);
        }
    }

    @Nested
    @DisplayName("객체 그래프 (이론 8.4)")
    class ObjectGraph {

        @Test
        @DisplayName("필드 하나가 Serializable이 아니면 전체 직렬화가 실패하고, 예외에 그 클래스 이름이 나온다")
        void nonSerializableFieldFails() {
            LoginUserBad user = new LoginUserBad("u1", "kim", new PointService());

            assertThatThrownBy(() -> SerializationUtils.serialize(user))
                    .isInstanceOf(NotSerializableException.class)
                    .hasMessageContaining("PointService");
        }

        @Test
        @DisplayName("데이터만 가진 세션 객체는 직렬화된다")
        void dataOnlyObjectWorks() {
            LoginUser copy = SerializationUtils.roundTrip(new LoginUser("u1", "kim"));

            assertThat(copy.getUserId()).isEqualTo("u1");
        }
    }

    @Nested
    @DisplayName("싱글턴 (이론 8.5)")
    class Singleton {

        @Test
        @DisplayName("readResolve가 없으면 역직렬화로 두 번째 인스턴스가 생긴다")
        void plainSingletonBreaks() {
            assertThat(SerializationUtils.roundTrip(SettingsBad.INSTANCE)).isNotSameAs(SettingsBad.INSTANCE);
        }

        @Test
        @DisplayName("readResolve는 기존 인스턴스로 교체한다")
        void readResolveKeepsSingleton() {
            assertThat(SerializationUtils.roundTrip(Settings.INSTANCE)).isSameAs(Settings.INSTANCE);
        }

        @Test
        @DisplayName("enum은 역직렬화 후에도 같은 상수다")
        void enumKeepsSingleton() {
            assertThat(SerializationUtils.roundTrip(EnumSettings.INSTANCE)).isSameAs(EnumSettings.INSTANCE);
        }
    }

    @Nested
    @DisplayName("역직렬화 필터 (이론 8.6)")
    class Filter {

        private final ObjectInputFilter onlyAccount = ObjectInputFilter.Config.createFilter(
                "study.serialization.account.Account;java.base/*;!*");

        @Test
        @DisplayName("허용 목록의 클래스는 역직렬화된다")
        void allowedClassPasses() throws Exception {
            byte[] bytes = SerializationUtils.serialize(new Account("kim", 100));

            Account account = SerializationUtils.deserialize(bytes, onlyAccount);

            assertThat(account.getBalance()).isEqualTo(100);
        }

        @Test
        @DisplayName("허용 목록 밖의 클래스는 객체가 만들어지기 전에 거부된다")
        void otherClassIsRejected() throws Exception {
            LegacyAccount.constructorCalls = 0;
            byte[] bytes = SerializationUtils.serialize(new LegacyAccount("kim", 100));

            assertThatThrownBy(() -> SerializationUtils.deserialize(bytes, onlyAccount))
                    .isInstanceOf(InvalidClassException.class)
                    .hasMessageContaining("REJECTED");
        }
    }
}
```

## 8. 변형 실습

### 실습 1. 진짜로 클래스를 바꿔서 UID 문제 겪기

1. `Account`를 파일로 저장하는 코드를 한 번 실행한다: `Files.write(Path.of("account.bin"), SerializationUtils.serialize(new Account("kim", 100)));`
2. `Account`에 `private String memo;` 필드를 **추가**하고 파일을 다시 읽는다.
   - **예상**: 성공, `memo`는 `null`. UID가 같으면 필드 추가는 호환된다.
3. `balance` 필드 타입을 `long` → `int`로 바꾸고 다시 읽는다.
   - **예상**: `InvalidClassException` (필드 타입 불일치). UID를 맞춰도 **호환되지 않는 변경**은 막을 수 없다.
4. `LegacyAccount`로 1번을 한 뒤 `public void noop() {}` 메서드만 추가하고 읽는다.
   - **예상**: `InvalidClassException: local class incompatible`. UID를 선언하지 않았을 때의 위험이다.

→ Redis 캐시에 이 객체가 들어 있다면, 배포 직후 무슨 일이 생길지 설명해본다 (이론 8.1, 9장).

### 실습 2. 상위 클래스가 `Serializable`이 아니면?

```java
public class BaseEntity {                 // Serializable 아님
    protected String createdBy = "system";
    public BaseEntity() { }               // 이 생성자를 지우면?
}

public class Order extends BaseEntity implements Serializable {
    private static final long serialVersionUID = 1L;
    private final String orderNo;
    public Order(String orderNo) { this.orderNo = orderNo; createdBy = "kim"; }
}
```

- `new Order("A-1")`을 왕복시키면 `createdBy`는 `"kim"`인가 `"system"`인가?
- `BaseEntity`의 무인자 생성자를 지우면 어떻게 되는가?
- **관찰 포인트**: 이론 5.2의 4번 단계 — "`Serializable`이 아닌 첫 상위 클래스의 무인자 생성자만 호출된다"를 직접 확인한다. (예상: `"system"`, 생성자를 지우면 `InvalidClassException: no valid constructor`)

### 실습 3. 같은 객체를 두 번 참조하면?

```java
List<Account> list = new ArrayList<>();
Account a = new Account("kim", 100);
list.add(a);
list.add(a);
List<Account> copy = SerializationUtils.roundTrip(list);
```

- `copy.get(0) == copy.get(1)`은 `true`인가 `false`인가?
- `a`를 두 번 따로 `serialize`해서 각각 `deserialize`하면 두 결과는 같은 객체인가?
- **관찰 포인트**: 이론 5.1의 3번 단계 — **한 스트림 안에서만** "이미 쓴 객체"를 참조 번호로 기록한다. 스트림이 다르면 참조 관계가 이어지지 않는다. (예상: 첫 번째는 `true`, 두 번째는 다른 객체)
