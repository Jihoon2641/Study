# final 필드 의미론 (final field semantics)

## 한 줄 정의
생성자가 끝났을 때 `final` 인스턴스 필드에 쓰인 값은, 그 객체의 참조를 얻은 모든 스레드에게 동기화 없이도 정확히 보인다는 자바 메모리 모델(JMM)의 보장. JLS 17.5에 정의되어 있다.

## 도입 버전
- Java 5+(JSR-133으로 개정된 자바 메모리 모델). Java 1.4 이전에는 이 보장이 없어서, `final` 필드도 다른 스레드에서 기본값으로 보일 수 있었다.
- Java 7 레거시를 포함해 현재 쓰는 모든 버전에 적용된다.

## 무엇을 하는가
`new Point(1, 2)`의 결과를 공유 변수에 넣는 코드는 기계어 수준에서 "메모리 할당 → 필드 쓰기 → 참조를 공유 변수에 쓰기" 순서다. 하지만 JIT 컴파일러와 CPU는 성능을 위해 서로 의존하지 않는 쓰기의 순서를 바꿀 수 있다. 그러면 다른 스레드가 참조는 보았는데 필드는 아직 `0`인 객체를 볼 수 있다.

`final` 필드는 이 재배치를 금지한다. JLS는 생성자 끝에 동결(freeze) 동작이 있다고 정의하고, 동결 이전의 `final` 필드 쓰기가 그 뒤의 참조 공개보다 먼저 보이도록 보장한다. 구현상으로는 JVM이 생성자 끝에 저장-저장(StoreStore) 메모리 배리어를 넣는다. `final` 필드를 통해 도달한 객체(예: `final int[] arr`가 가리키는 배열의 생성자 시점 내용)까지 보장이 이어진다.

조건은 하나다. 생성자 도중에 `this`가 다른 스레드로 새어 나가지 않아야 한다.

## 최소 사용 예
```java
class Holder {
    final int x;          // 보장됨: 참조를 본 스레드는 항상 42를 본다
    int y;                // 보장 안 됨: 0 이 보일 수 있다
    Holder() { x = 42; y = 42; }
}

static Holder shared;     // volatile 아님 — 데이터 경쟁(data race)으로 공개
// 스레드 A: shared = new Holder();
// 스레드 B: Holder h = shared; if (h != null) { h.x; /* 42 */ h.y; /* 0 또는 42 */ }
```

## 자주 하는 오해 / 헷갈리는 짝
- **final vs volatile** — 기준은 "값이 나중에 바뀌는가"이다. `final`은 생성 시점에 한 번 쓰인 값의 가시성을 보장한다. `volatile`은 바뀔 때마다 새 값의 가시성을 보장한다. 생성 후 안 바뀌면 `final`, 바뀌면 `volatile`(또는 락)이다.
- **사실상 불변(effectively immutable)이면 충분하다** — 아니다. 필드를 한 번도 바꾸지 않아도 `final`이 없으면 위의 `y`처럼 보장이 없다. 이 경우 `volatile` 필드나 동시성 컬렉션 같은 안전한 공개(safe publication)를 거쳐야 한다.
- **`static final` 필드** — 이 경우는 JLS 17.5가 아니라 클래스 초기화 규칙이 가시성을 보장한다. 클래스 초기화는 JVM이 락을 잡고 수행하므로, 초기화가 끝난 클래스의 정적 필드는 모든 스레드에게 보인다.
