# 실패 원자성 (failure atomicity)

## 한 줄 정의
메서드 호출이 예외로 실패해도 객체가 호출 전 상태를 그대로 유지하는 성질.

## 도입 버전
- 설계 성질이라 모든 버전에 해당한다. Java 7 레거시에서도 같은 기법을 쓸 수 있다.
- 불변 객체와 `List.copyOf`(Java 10+) 같은 복사 API가 이 성질을 얻기 쉽게 해 준다.

## 무엇을 하는가
여러 필드를 차례로 바꾸는 메서드가 중간에 예외를 던지면, 일부 필드만 바뀐 상태가 남는다. 호출자는 예외를 잡더라도 객체가 어떤 상태인지 알 수 없다. 재시도하면 이미 반영된 단계가 한 번 더 반영될 수 있다.

실패 원자성을 얻는 방법은 대략 네 가지다. 위에 있을수록 먼저 고려한다.
1. 불변 객체로 설계한다. 상태가 안 바뀌니 원자성이 공짜다.
2. 상태를 바꾸기 전에 모든 검증을 끝낸다. 예외가 날 수 있는 코드를 변경 코드보다 앞에 둔다.
3. 복사본에서 작업한 뒤, 성공하면 결과로 원본을 교체한다.
4. 실패하면 되돌리는 복구 코드를 쓴다. 주로 디스크 기반 자료구조에서 쓰며 가장 번거롭다.

`ArrayList.add`가 좋은 예다. 용량을 먼저 늘리고(`OutOfMemoryError`가 나도 기존 원소와 `size`는 그대로), 그 뒤에 원소를 넣고 `size`를 증가시킨다.

## 최소 사용 예
```java
// 방법 2: 검증을 변경보다 앞에
public Object pop() {
    if (size == 0) throw new EmptyStackException();   // 상태를 바꾸기 전에 실패
    Object result = elements[--size];
    elements[size] = null;
    return result;
}
```
`if` 검사가 없어도 `elements[-1]`에서 `ArrayIndexOutOfBoundsException`이 나긴 한다. 하지만 그때는 이미 `--size`로 `size`가 `-1`이 된 뒤다.

## 자주 하는 오해 / 헷갈리는 짝
- **실패 원자성 vs 트랜잭션 원자성** — 기준은 "범위가 객체 하나인가, 여러 자원인가"이다. 실패 원자성은 객체 하나의 메모리 상태에 대한 성질이다. DB 트랜잭션은 여러 테이블과 자원에 걸친 원자성을 롤백으로 보장한다. 객체가 실패 원자적이어도 DB 반영은 별도로 트랜잭션으로 묶어야 한다.
- **항상 달성해야 한다** — 책도 권장 사항으로 본다. 동시 수정 오류(`ConcurrentModificationException`)처럼 실패 원자성을 보장할 수 없는 경우도 있고, 비용이 큰 경우도 있다. 달성하지 못하면 실패 후 객체 상태를 API 문서에 적어야 한다.
- **`Error`도 대상인가** — `OutOfMemoryError` 같은 `Error`는 보통 복구를 기대하지 않으므로 실패 원자성을 억지로 챙길 필요는 없다.
