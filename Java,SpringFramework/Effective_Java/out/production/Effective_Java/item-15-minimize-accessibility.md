# 아이템 15. 클래스와 멤버의 접근 권한을 최소화하라

## 1. 한 줄 결론

모든 클래스와 멤버는 **컴파일이 되는 가장 낮은 접근 수준에서 출발**해야 하고, 수준을 올리는 건 "외부가 실제로 필요로 한다"는 근거가 생겼을 때뿐이다. 한 번 `public`으로 열면 그건 취향이 아니라 **영원히 지켜야 할 약속(API)** 이 되기 때문이다.

## 2. 신입 눈높이 설명

`private`/`public`을 "숨김/공개" 정도로 이해하면 절반만 맞다. 진짜 의미는 **"내가 앞으로 마음대로 바꿔도 되는 영역이 어디까지인가"를 선언하는 행위**다.

`private` 필드는 내일 이름을 바꾸든 타입을 바꾸든 삭제하든 내 클래스 안에서만 고치면 끝난다. 그런데 같은 필드를 `public`으로 열어 둔 순간, 그 필드를 읽는 코드가 사내 어느 모듈에 몇 군데나 있는지 나는 알 수 없고, 이름 하나 바꾸는 데 다른 팀의 승인이 필요해진다. 즉 접근 제한자는 보안 장치이기 전에 **변경 비용을 통제하는 장치**다.

비유하자면 건물 출입증 등급과 같다. 전 직원에게 서버실 카드를 한 번 뿌리고 나면, 나중에 회수하는 건 뿌리는 것보다 백 배 어렵다. 그래서 처음부터 최소 등급으로 주고, 필요하다는 요청이 올 때 올린다.

책이 정리한 규칙을 그대로 압축하면 이렇다.

- 톱레벨(top-level) 클래스·인터페이스에 줄 수 있는 건 `public`과 package-private 둘뿐이다. 한 패키지 안에서만 쓴다면 package-private으로 선언하라. 그러면 그건 API가 아니라 **내부 구현**이 되고, 다음 릴리스에서 마음대로 지울 수 있다.
- 한 클래스에서만 쓰는 package-private 톱레벨 클래스는 그 클래스 안에 **private 정적 중첩 클래스(private static nested class)** 로 넣어라. 노출 범위가 패키지 → 클래스 하나로 줄어든다.
- 멤버는 `private` → package-private → `protected` → `public` 순으로 필요한 만큼만 올린다. `private`에서 package-private으로 올리는 건 비교적 가볍지만, **package-private에서 `protected`로 올라가는 순간 노출 범위가 급격히 커진다.** `protected` 멤버는 그 클래스를 상속한 외부 코드 전부가 쓸 수 있는 공개 API이고, 영원히 지원해야 한다.
- `public` 클래스의 인스턴스 필드는 되도록 `public`이 아니어야 한다. 필드가 열려 있으면 그 필드에 담기는 값을 제한할 힘(불변식)을 잃고, 필드가 수정될 때 다른 작업을 끼워 넣을 수도 없으며, 스레드 안전성도 보장할 수 없다.
- 예외: 상수라면 `public static final`로 공개해도 된다. 단 **반드시 기본 타입이거나 불변 객체를 참조해야 한다.** 가변 객체를 참조하는 상수는 아래 3-2가 말하는 사고를 낸다.

## 3. 원리 — 왜 그런가

### 3-1. 접근 제어자는 주석이 아니라 클래스 파일에 박히는 플래그다

`private`, `public` 같은 수식어는 컴파일러가 소스에서 검사하고 버리는 힌트가 아니다. 클래스 파일 포맷의 `access_flags`(클래스), `field_info.access_flags`, `method_info.access_flags`에 `ACC_PRIVATE(0x0002)`, `ACC_PROTECTED(0x0004)`, `ACC_PUBLIC(0x0001)` 비트로 그대로 기록된다. 플래그가 하나도 없으면 package-private이다.

그래서 접근 위반은 두 번 걸러진다. 컴파일 시점에 javac가 거르고, 런타임에 JVM이 **링킹(linking) 단계의 해석(resolution)** 에서 다시 검사한다(JVMS 5.4.4 접근 제어). 즉 `A.java`를 짤 때 `B.field`가 `public`이라 통과시켜 컴파일해 두고, 나중에 `B`만 `private`으로 고쳐 재컴파일한 뒤 `A.class`는 예전 것을 그대로 쓰면 — 실행 중 그 줄에 도달하는 순간 `IllegalAccessError`가 터진다. 컴파일 에러가 아니라 **런타임 에러**다. 접근 수준을 낮추는 변경이 "바이너리 호환성(binary compatibility)을 깨는 변경"으로 분류되는 이유가 이것이고, 곧 한 번 올린 수준을 되돌리기 어려운 이유이기도 하다.

### 3-2. `final`은 "참조"만 고정한다 — public static final 배열의 보안 허점

책이 아이템 15에서 가장 강하게 경고하는 코드가 이것이다.

```java
// 보안 허점이 숨어 있다
public static final Thing[] VALUES = { ... };
```

`final` 필드에 대한 JLS 4.12.4의 보장은 **"변수에 한 번 대입된 값은 바뀌지 않는다"** 이다. 여기서 "값"은 배열 객체가 아니라 **배열을 가리키는 참조**다. 바이트코드로 보면 차이가 선명하다.

- `VALUES = new Thing[0];` → `putstatic` 명령. final 필드에 대한 `putstatic`은 그 클래스의 `<clinit>` 밖에서는 허용되지 않는다. 그래서 컴파일도 안 된다.
- `VALUES[0] = x;` → `aastore` 명령. 이건 **배열 객체에 대한 연산이지 필드에 대한 연산이 아니다.** final 여부와 아무 상관이 없어 조용히 통과한다.

결과적으로 `public static final` 배열은 "누구나 내용을 바꿀 수 있는 전역 변수"다. 예제 파일 `Item15Example.java`의 main이 이 장면을 실제로 재현한다.

해결책은 두 가지다.

```java
// (1) 배열은 private으로 감추고, 불변 리스트를 공개한다  — Java 1.2+
private static final Thing[] PRIVATE_VALUES = { ... };
public static final List<Thing> VALUES =
        Collections.unmodifiableList(Arrays.asList(PRIVATE_VALUES));

// (2) 배열 타입을 유지해야 한다면 복사본을 반환한다  — 모든 버전
private static final Thing[] PRIVATE_VALUES = { ... };
public static Thing[] values() { return PRIVATE_VALUES.clone(); }
```

`(Java 9+)` 원소를 인라인으로 적을 수 있다면 `List.of(...)`가 더 낫다. `unmodifiableList`는 원본 리스트를 감싼 **뷰(view)** 라서 원본이 바뀌면 뷰도 따라 바뀌지만, `List.of`는 값을 복사해 담는 진짜 불변 리스트다. `(Java 10+)`에는 기존 컬렉션으로부터 만드는 `List.copyOf` / `Set.copyOf` / `Map.copyOf`도 있다.
`(Java 7 프로젝트)` `List.of`는 못 쓴다. 위 (1)번 형태가 그대로 대안이고, 예제 파일의 `Legacy7` 클래스가 이것이다.

`clone()`과 불변 리스트 중 고르는 기준은 하나다. **호출자가 결과를 수정할 일이 있으면 `clone()`(호출마다 복사 비용 발생), 읽기만 한다면 불변 리스트(복사 비용 0).** 상수 목록은 대개 후자다.

### 3-3. 컴파일 타임 상수는 사용처에 복사되어 박힌다

이건 책에 없지만 `public static final`을 논할 때 반드시 알아야 하는 함정이다.

`static final`이면서 기본 타입 또는 `String`이고 초기화 식이 상수 식이면, JLS 4.12.4가 말하는 **상수 변수(constant variable)** 가 된다. 이때 javac는 사용처에서 `getstatic`을 내보내지 않고 **값 자체를 바이트코드에 인라인**한다(JLS 13.1).

```java
// Config.java (라이브러리)
public static final int MAX_RETRY = 3;

// App.java (사용처) → 컴파일되면 그냥 iconst_3 이 박힌다
if (count < Config.MAX_RETRY) { ... }
```

라이브러리에서 `MAX_RETRY`를 5로 고쳐 새 jar를 배포해도, **사용처를 재컴파일하지 않으면 그 앱은 계속 3으로 동작한다.** 실행 중에 `Config` 클래스를 참조조차 하지 않으므로 디버깅해도 원인이 안 보인다. 값이 바뀔 여지가 있는 설정값은 상수로 공개하지 말고 `static` 메서드 뒤에 두는 편이 안전하다. (배열은 상수 변수가 아니므로 인라인되지 않는다 — 3-2의 문제와는 별개의 이야기다.)

### 3-4. 재정의할 때는 접근 수준을 좁힐 수 없다

JLS 8.4.8.3이 못 박은 규칙이다. 상위 클래스의 메서드를 재정의하면서 접근 수준을 더 좁게 만들면 컴파일 에러다. 이유는 **리스코프 치환 원칙(Liskov substitution principle)** 이다. 상위 타입을 쓸 수 있는 자리라면 하위 타입도 쓸 수 있어야 하는데, `Sub`가 `toString()`을 package-private으로 좁혀 놓으면 `Object o = new Sub(); o.toString();` 이라는 멀쩡한 코드가 깨진다.

여기서 따라오는 실무 결론 하나: **인터페이스를 구현하면 그 메서드들은 전부 `public`이 된다.** 인터페이스 메서드는 암묵적으로 `public`이기 때문이다. 그러니 "이 클래스가 무엇을 구현할 것인가"를 정하는 일은 곧 "무엇을 영원히 공개할 것인가"를 정하는 일이다. 인터페이스를 가볍게 늘리지 말라는 말이 여기서 나온다.

### 3-5. private 중첩 클래스와 nestmates — Java 11에서 조용히 달라진 것

`private static class Inner`가 바깥 클래스의 `private` 필드에 접근하는 코드는 흔하다. 그런데 JVM 입장에서 둘은 **완전히 별개의 클래스**(`Outer.class`, `Outer$Inner.class`)라서, 원래 JVM 접근 규칙상 남의 `private`에는 손댈 수 없다.

Java 10까지 javac는 이걸 우회하려고 **합성 접근 메서드(synthetic access method)** `access$000` 같은 걸 자동 생성했다. 이 메서드의 접근 수준은 package-private이었다. 즉 소스에서는 `private`이라고 썼지만, **바이트코드 레벨에서는 같은 패키지의 아무 클래스나 호출할 수 있는 우회로**가 뚫려 있었다.

`(Java 11+)` JEP 181(Nest-Based Access Control)이 이 구멍을 막았다. 클래스 파일에 `NestHost` / `NestMembers` 속성이 생겨서, JVM이 "같은 둥지(nest)에 속한 클래스끼리는 private 접근을 허용한다"고 직접 판단한다. 합성 메서드가 사라져 클래스 파일도 작아지고 우회로도 없어졌다. Java 8~10 환경에서 `private`의 캡슐화가 이론만큼 완벽하지 않았다는 사실은 알아 둘 만하다.

## 4. 심화 / 예외 상황

**테스트 때문에 수준을 푸는 문제.** 책은 `private`을 package-private까지 푸는 것은 허용하되 **그 이상은 안 된다**고 못 박는다. 테스트 코드를 같은 패키지에 두면(메이븐/그레이들이 `src/test/java` 아래에 같은 패키지 경로를 만들게 하는 관례가 정확히 이걸 노린 것이다) package-private 멤버를 그대로 테스트할 수 있다. 반대로 "테스트하기 어려우니 `public`으로 열자"는 거의 항상 설계 신호다 — 그 private 로직이 사실 별도 클래스로 분리돼야 한다는 뜻인 경우가 많다.

**모듈 시스템은 책의 설명이 가장 낡은 부분이다.** `(Java 9+)` 3판은 모듈을 "패키지 수준의 네 번째 접근 수준"으로 소개하면서 "주의해서 쓰라"고만 한다. 지금 시점에서는 좀 더 단정적으로 말할 수 있다. 애플리케이션 코드에서 모듈 시스템 채택률은 여전히 낮고(대부분 클래스패스로 돈다), 반대로 **JDK 자신은 완전히 강하게 캡슐화되었다.** `(Java 16, JEP 396)` JDK 내부 API에 대한 리플렉션 접근이 기본 거부로 바뀌었고, `(Java 17, JEP 403)` 이를 풀던 `--illegal-access` 옵션이 아예 제거됐다. 이제 `setAccessible(true)`로 남의 `private`을 여는 코드는 대상 모듈이 `opens` 하지 않았다면 `InaccessibleObjectException`을 던진다. "리플렉션이면 어차피 뚫린다"는 옛 상식이 더 이상 그대로 성립하지 않는다는 뜻이고, 접근 제한자의 무게가 오히려 무거워졌다.

**`protected`는 생각보다 훨씬 비싸다.** `protected` 멤버는 하위 클래스뿐 아니라 **같은 패키지의 모든 클래스**도 접근할 수 있다(JLS 6.6.1~6.6.2). 게다가 상속용으로 노출한 순간 아이템 19가 요구하는 "재정의 가능 메서드의 자기사용(self-use) 패턴 문서화" 의무가 따라붙는다. 웬만하면 `protected` 멤버 수는 0에 가깝게 유지하는 게 맞다.

**직렬화의 뒷문.** `Serializable`을 구현하면 `private` 인스턴스 필드들이 **직렬화 형태(serialized form)라는 공개 API로 새어 나간다.** 접근 제한자로 아무리 숨겨도 바이트 스트림에는 필드 이름과 값이 그대로 들어가고, 한번 배포되면 필드 이름조차 마음대로 못 바꾼다. 이게 12장(직렬화)이 통째로 다루는 주제다.

**`record`와 접근 제한.** `(Java 16+)` 레코드는 필드를 `private final`로, 접근자를 `public`으로 강제한다. 접근 제한 관점의 기본기는 잡혀 있는 셈이다. 다만 **컴포넌트가 배열이나 가변 객체면 3-2의 문제가 그대로 재현된다.** 레코드의 기본 접근자는 참조를 그대로 돌려주기 때문이다. 이 경우 compact 생성자에서 복사해 받고 접근자를 직접 재정의해 복사해 돌려줘야 한다.

**실무 함정 — 프레임워크가 접근 수준을 본다.** 스프링 AOP의 프록시(`@Transactional`, `@Cacheable`, `@Async` 등)는 `public` 메서드에만 적용된다. 캡슐화를 지킨답시고 `@Transactional`을 `private`이나 package-private 메서드에 붙이면 **에러 없이 조용히 무시되고 트랜잭션이 안 걸린다.** 접근 수준 최소화 원칙과 충돌하는 지점인데, 해결은 "메서드를 public으로 여는 것"이 아니라 "트랜잭션 경계가 될 만한 메서드를 별도 빈으로 분리하는 것"이다. 즉 프레임워크 제약 때문에 캡슐화를 포기하지 말고 설계를 나누라는 뜻이다.

## 5. 함께 보면 좋은 아이템

이 아이템은 4장(클래스와 인터페이스)의 출발점이다. 15가 "얼마나 감출 것인가"를 정하면 16~17이 "감춘 뒤 어떻게 다룰 것인가"를 잇는다.

- **아이템 16. public 클래스에서는 public 필드가 아닌 접근자 메서드를 사용하라** — 15가 말한 "public 클래스의 인스턴스 필드는 public이면 안 된다"를 클래스 단위로 구체화한 아이템이다. 15를 읽고 바로 이어 읽어야 맥락이 끊기지 않는다.
- **아이템 17. 변경 가능성을 최소화하라** — 접근 제한이 캡슐화의 절반이라면, 불변성이 나머지 절반이다. 3-2에서 본 `public static final` 배열 사고는 "감추지 않아서"이기도 하지만 근본적으로는 "가변이라서" 터진 일이다.
- **아이템 50. 적시에 방어적 복사본을 만들라** — `private`으로 감춰도 게터에서 내부 참조를 그대로 돌려주면 캡슐화는 뚫린다. 예제의 `clone()` 반환이 바로 이 아이템의 축소판이다.

## 6. 확인 질문

예제의 `GoodClone.values()`는 `PRIVATE_VALUES.clone()`을 돌려주니 호출자가 배열을 아무리 헤집어도 원본 배열은 안전하다. 그런데 만약 `Thing`이 불변이 아니라 `setName(String)` 같은 세터를 가진 가변 클래스라면, 이 `clone()` 방어는 여전히 유효할까? 유효하지 않다면 정확히 어떤 호출 한 줄로 원본이 오염되는가?
